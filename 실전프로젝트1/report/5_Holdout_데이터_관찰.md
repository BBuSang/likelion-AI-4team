# 실전 1 보고서 2부 ⑤ Holdout 데이터 관찰

> - **과제**: 금융사 사내 문서에서 개인정보 7종을 찾는 탐지기를 규칙 기반·토큰 분류·LLM 세 방식으로 비교하고, 운영에 쓸 탐지기를 근거 있게 고른다.
> - **데이터**: 제공 `pii_synth_finance` dev 100건(정답 548개) · test 200건(정답 1,165개) / 추가 시험 데이터: 엣지 케이스 64건(정답 116개), 일상 문서 1,983건(정답 3,375개) / **멘토 holdout 187건(정답 912개)**
> - **채점**: 멘토 제공 `run_compare.py` (strict·partial 정밀도/재현율/F1, mask_rec, 라벨별·어려운 사례 재현율, 일관성)
> - **작성**: 2026-10-26 · 저장소 `hosung` 브랜치 `실전프로젝트1/` · 작업 기록 전체는 `worklog.md` (21~24장)

**보고서 구성**: 0 요약 및 결론 · **1부** ① 데이터 관찰 리포트 · ② 방식별 비교표 · ③ 오류 유형 분석 · ④ 탐지기 선정 근거 · **2부** ⑤ Holdout 데이터 관찰 · ⑥ Holdout 성능 · ⑦ Holdout 오류 분석 · ⑧ Holdout 개선 내역 · 부록 개선 과정과 데이터 사용 기록 (`report/` 폴더)

> **2부 진행 순서**: holdout 받음 → 탐지기를 고치지 않고 **먼저 채점·기록**(⑥ 개선 전) → 데이터 관찰(⑤) → 오류 분석(⑦) → 개선과 재채점, dev·test 재확인(⑧).
> 개선 후 holdout 점수는 holdout 오류를 보고 맞춘 값이라 **일반화 성능이 아니다.**

---

멘토 배포 파일 `holdout/holdout_labeled.jsonl`을 dev·test와 같은 방법으로 라벨별로 모아(`data/gold_by_label_holdout/<라벨>.csv`) 비교했다. holdout에는 `template`, `person_id`, `roles` 필드가 없어 템플릿 비교·같은 사람 묶기는 하지 않았다.

## 5-5. 해석

- holdout은 **처음 보는 문서 유형 19종 + 다양한 표기**로, dev·test의 "같은 템플릿·형식 한 가지" 한계를 정확히 겨냥한 데이터다.
- 새로 생긴 형식 대부분은 **팀이 엣지 케이스·일상 문서로 미리 대비했던 것**이다: 국제번호 `+82`, 은행별 계좌 자릿수, 붙여쓰기·공백 카드·주민번호, 지번·시도 줄임말 주소, 외자·복성 이름, 건물명 + 동·호수. 개선 전 점수가 유지된 이유로 본다(⑥, mask_rec 0.993).
- 미리 대비하지 못한 것: 이름 뒤 새 결합(`에게`, `인데요`, `의`), 한 글자 이름, 주소 앞 우편번호, 계좌 3-2-6-1 같은 마지막 1자리 형식, 새 문서 유형의 서식 항목(`소명자:`, `위임인:`) → ⑦ 오류 분석에서 확인했다.
