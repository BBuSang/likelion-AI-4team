## A-1. 원칙

- **개선은 dev로만** 하고, test는 중간 확인에만 쓴다(멘토 안내).
- 멘토 holdout을 받기 전에는, 일상 문서 1,983건을 반으로 나눠 **개선용(synth_dev 989건)**과 **오류를 끝까지 보지 않는 holdout(synth_holdout 994건)**으로 썼다.

## A-2. 실제 사용 기록 (그대로 밝힘)

| 시점 | test 사용 | 비고 |

## A-4. 2차 평가 세트와 v9 개선

dev·test·엣지·일상 문서·멘토 holdout을 모두 한 번 이상 보고 고쳐서, 처음 보는 문서 성능을 깨끗하게 잴 세트가 없어졌다. 그래서 OpenAI gpt-4.1로 두 세트를 새로 만들었다(worklog 26~28장).

| 세트 | 문서 / 정답 | 내용 | 용도 |
|---|---|---|---|
| synth_fresh | 1,775 / 5,918 | dev·test·holdout에 없던 금융 업무 문서 25종, 문서마다 표기 계획을 무작위로 지정 | **평가 전용** (고치는 데 안 씀) |
| synth_hard_dev | 379 / 1,892 | 일부러 어렵게 만든 표기: 외자·일반 단어 같은 이름·메신저 호격·부서에 붙은 이름·`at` 이메일·붙여 쓴 지역번호 등 | **개선용** (오류를 봄) |
| synth_hard_eval | 403 / 1,958 | 같은 방식, 나머지 반 | **평가용** (점수만) |

**정답 품질 관리**: 생성 모델이 어려운 값의 표시를 절반 가까이 빠뜨려서(hard 표시 2,716 → 보정 후 4,675) 다른 호출로 **표시를 보정**하고, 팀 기준을 넣은 검수에서 문제가 나온 문서는 **고치지 않고 뺐다**(fresh 9%, hard 17%). 우리 탐지기는 정답 만들기에 쓰지 않았다.

**v8 그대로 첫 채점 → v9 (규칙 + 토큰)**

| 데이터 | 역할 | strict P | strict F1 | mask_rec |
|---|---|---|---|---|
| synth_hard_dev | 개선용 | 0.790 → 0.868 | 0.799 → 0.875 | 0.951 → 0.978 |
| **synth_hard_eval** | 평가용 | 0.787 → **0.871** | 0.781 → **0.861** | 0.933 → **0.964** |
| **synth_fresh** | 평가 전용 | 0.855 → **0.920** | 0.855 → **0.920** | 0.976 → **0.983** |
| 일상 문서 평가용 | | 0.934 → 0.939 | 0.956 → 0.961 | 0.988 → 0.989 |
| dev · test · 엣지 · 멘토 holdout | | 그대로 | 그대로 | 그대로 |

- 개선용 반에서 찾은 가장 큰 원인: 규칙이 서식 칸 `예약자: 최민재님`을 조사째 이름으로 잡아 문서 전체로 퍼뜨리고, 합칠 때 규칙이 우선이라 토큰이 맞힌 `최민재`를 덮어씀. 합집합이 토큰 단독보다 나빠진 69건이 모두 이런 규칙 쪽 잘못이었다
- 남은 한계: **이름 재현율은 거의 그대로**(평가용 반 0.836 → 0.843). `하늘`·`가람` 같은 일반 단어 이름, 호격, 성 없는 이름은 문맥 없이 일반 단어와 구분하기 어렵다. 평가용 반 정밀도 0.871은 하한선 0.90 아래(어려운 표기만 모은 세트)
- v10(`이`로 끝나는 이름 처리) 뒤: 평가용 반 strict F1 0.861 → 0.866, fresh 0.920 → 0.923, 다른 세트는 그대로. 9개 세트에서 떨어진 지표 없음
- 주의: fresh와 hard는 같은 생성 프롬프트 계열이라, fresh 개선 폭에는 같은 생성기 표기 습관에 맞춘 효과가 섞여 있을 수 있다
