## 3. 이름: 표기 형태가 다양하다

### 3-1. 표기 형태

| 형태 | 예 | dev | test |
| --- | --- | --- | --- |
| 전체 이름 (full) | `윤선영` | 298 (88%) | 680 (88%) |
| 띄어 쓴 이름 (spaced) | `윤 선영` | 27 (8%) | 51 (7%) |
| 성 없이 이름만 (given) | `지영아`, `소율 씨` | 15 (4%) | 44 (6%) |

같은 사람이 한 문서 안에서 다르게 쓰이기도 합니다. (예: `윤 선영 고객` … `윤선영은`) dev에서 27명, test에서 41명이 두 가지 이상의 모양으로 나옵니다.

### 3-2. 이름 바로 뒤에 오는 말 (test)

| 뒤에 오는 말 | 개수 | 비율 |
| --- | --- | --- |
| 공백·문장부호·줄바꿈 등 | 410 | 53% |
| `고객` | 79 | 10% |
| **조사** (`은/는/이/가/을/를/이랑`…) | 52 | 7% |
| `님` | 42 | 5% |
| 직급 (`부장`, `팀장`, `책임`, `매니저`, `대리`, `과장`) | 131 | 17% |
| `씨`, `드림` | 36 | 5% |

- 이름 뒤에 **조사가 붙는 경우가 약 11%** 입니다 (조사로 시작하는 말 전체 기준). 정답 범위에는 조사가 **빠져 있으므로**, 조사까지 잡으면 경계 오류가 됩니다.
- 이름의 절반 가까이는 뒤에 **호칭·직급**이 붙습니다 → 규칙 기반이 이름을 찾는 가장 좋은 단서

### 3-3. 성 없이 이름만 쓰는 경우 (given)
- 거의 전부 **직원끼리 부르는 말**입니다: 메신저 `지영아, …`, 회의록 `소율 씨가 검토`, 메일 `서연 씨, 안녕하세요`
- 일반 성씨 목록으로는 찾을 수 없어서 **가장 어려운 유형**으로 예상했고, 실제로 규칙 기반이 놓친 13개가 모두 이 유형이었습니다.

### 3-4. 동명이인 (4쌍)
| 이름 | 인물 | 구분 단서 |
| --- | --- | --- |
| 김민준 | P066(직원, 회의 참석) / P067(민원 고객) | 문맥 (직급 vs `고객`) |
| 이서연 | P068 / P069 | 문맥 |
| 박도윤 | P070 / P071 | 소속 팀 |
| 정하은 | P072 / P073 (test에만) | 문맥 |

탐지 단계에서는 둘 다 `person`이면 되지만, **실전 2 가명처리에서 이름만으로 토큰을 만들면 두 사람이 한 토큰으로 합쳐집니다** (과제 질의 Q19·Q20).

- 대표번호는 `1599-0000` **하나뿐**입니다 (`1577`, `1588` 같은 다른 번호는 없음).
- 12자리 민원번호는 앞뒤 숫자 경계를 확인하지 않으면 전화번호·계좌번호로 잘못 잡힐 수 있습니다.

### 팀 기준: `김 과장`은 개인정보인가?
- 데이터에는 `허 부장님`, `남 부장이`처럼 **성 + 직함만** 있는 표현이 dev 17건, test 40건 문서에 나오고, **정답 라벨이 없습니다**.
- **우리 기준: 개인정보가 아니다.** 이름이 없어서 성 하나로는 사람을 특정하기 어렵고, 데이터의 라벨 기준과도 맞습니다. 그래서 탐지기가 이걸 잡으면 오탐으로 봅니다.
- 다만 같은 부서에 성이 같은 사람이 한 명뿐이라면 특정이 가능하므로, 실제 운영에서는 다시 검토할 여지가 있습니다.

## 7. dev와 test는 무엇이 다른가

| 항목 | 결과 |
| --- | --- |
| 문서 틀(템플릿) | **23종 똑같음** — dev에만 있거나 test에만 있는 틀이 없음 |
| 등장 인물 | test 72명 중 65명이 dev에도 나옴 |
| 숫자 형식 | 같음 |
| 문서 유형 구성 | dev는 **상담 문서**(대출 15%, 카드 분실 13%)가 많고, test는 **사내 문서**(업무메일 14%, 회의록 11%, 메신저 6.5%)가 많음 |
| 어려운 사례 비율 | test가 조금 더 많음 (성 없는 이름 4.4% → 5.7%, 조사 붙은 이름 문서 22% → 26%) |

**의미**
- dev를 보고 만든 규칙은 test에서도 대부분 통합니다 (실제로 규칙 재현율 dev 0.996 → test 0.989).
- 하지만 test 점수가 **"처음 보는 문서"에서의 성능을 보장하지 않습니다.** holdout은 새 문서 틀 16종과 새 인물로 만들어져 있어서, 그때 진짜 일반화 성능이 드러납니다.

## 8. 형태소 분석기(Kiwi)는 어떻게 쪼개나

| 문장 | Kiwi 결과 | 해석 |
| --- | --- | --- |
| `윤선영은` | 윤(고유명사) + 선영(일반명사) + 은(조사) | 조사는 잘 떼지만 이름을 한 덩어리로 못 봄 |
| `윤 선영` | 윤(고유명사) + 선영(일반명사) | 띄어 쓰면 따로 놂 |
| `한결 플러스 카드` | 한결(부사) + 플러스 + 카드 | 이름으로 오해하지 않음 ✅ |
| `정서현입니다` | 정서현(고유명사) + 입니다 | 잘 잡음 ✅ |
| `남궁다은` | 남궁다은(일반명사) | 두 글자 성은 고유명사로 못 봄 |

- dev 정답 이름 340개 중 Kiwi가 **고유명사 한 덩어리로 잡은 것은 157개(46%)** 뿐이고, 이름이 아닌 고유명사(지명·회사명·성 한 글자)도 308개 나왔습니다.
- → Kiwi만으로 이름을 찾을 수는 없고, 규칙의 **보조 단서**로만 씁니다.

## 9. 왜 `personas.json`(인물 목록)을 이름 사전으로 쓰면 안 되나

- `personas.json`은 데이터를 만들 때 쓴 **정답 인물 목록**입니다. 이걸 사전으로 쓰면 탐지기가 "이름을 찾는" 게 아니라 **"정답 목록과 맞춰 보는"** 것이 되어, 시험 전에 답지를 보는 것과 같습니다.
- 실제 금융사에서는 새 고객이 계속 생기므로 이런 목록이 없습니다. 점수는 높게 나와도 **운영에서는 전혀 통하지 않는** 탐지기가 됩니다.
- 그래서 **일반 성씨 목록**(김·이·박… + 남궁·황보 같은 두 글자 성)까지만 썼습니다.

## 10. 탐지기가 어려워할 곳 (예측 → 실제)

(전체 기준의 예측과 결과입니다. 고객 기준으로는 아래 첫 줄과 둘째 줄의 어려움이 **모두 직원 쪽 이야기**였고, rules v4는 test 고객 개인정보 458개를 하나도 놓치지 않았습니다.)
