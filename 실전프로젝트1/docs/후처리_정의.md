# 후처리 정의

> 비교표의 `(프롬프트만)`, `+ 형식 정리`, `+ 후처리`가 정확히 무엇을 하는지 정의합니다.
> 규칙은 코드(`detectors/llm_hcx.py`, `tools/merge_rules_llm.py`)에 들어 있는 것을 그대로 옮겼습니다.

---

## 1. 후처리란

**탐지기가 낸 결과를 받아서, 새로 찾지 않고 고치거나 버리는 단계**입니다.

- 후처리는 문서에서 개인정보를 **새로 찾지 않습니다.** 탐지기(LLM)가 이미 답한 것만 다룹니다.
- 이 프로젝트의 후처리는 모두 **사람이 쓴 규칙**입니다. 그래서 "LLM 결과"라고만 하지 않고 "LLM + 규칙 후처리"라고 밝힙니다.
- 후처리 규칙은 **dev 결과를 보고 만들었고**, test는 확인만 했습니다. test를 보고 고친 규칙은 없습니다.

**후처리는 두 가지**입니다.

| | 후처리 1: 형식 정리 | 후처리 2: 하이브리드 후처리 |
| --- | --- | --- |
| 언제 | LLM 답을 받은 **직후** | 규칙 기반과 LLM을 **합칠 때** |
| 대상 | LLM 답 **전체** | LLM이 **새로 더하려는 것**만 (규칙 v4가 찾은 것은 건드리지 않음) |
| 목적 | LLM이 **지시한 모양**을 안 지킨 것을 바로잡기 | LLM이 더한 것 중 **개인정보가 아닌 것**을 버리기 |
| 고치기 / 버리기 | 둘 다 함 (라벨 고치기, 직함 떼기, 버리기) | 버리기만 함 |
| 코드 | `detectors/llm_hcx.py`의 `post_process()` | `tools/merge_rules_llm.py`의 `keep()` |

---

## 2. 후처리가 아닌 "기본 처리" (모든 LLM 행에 들어 있음)

아래는 LLM 답을 채점 가능한 형식으로 바꾸는 **필수 변환**이라 `(프롬프트만)` 행에도 들어 있습니다. 후처리로 세지 않지만, 결과에 영향을 주므로 밝혀 둡니다.

| 단계 | 하는 일 | 이유 |
| --- | --- | --- |
| JSON 읽기 | LLM 답에서 `{"entities": [...]}`를 꺼냄 | |
| └ HCX만 | JSON이 깨지면 "다시 써 달라"고 최대 2번 재요청. 그래도 깨지면 `"label"`·`"text"` 짝만 건짐 | 깨진 답 때문에 문서 전체를 잃지 않으려고 |
| └ OpenAI만 | 형식 강제(structured outputs)로 항상 올바른 JSON, 라벨은 7종 중 하나만 | |
| 위치 찾기 | LLM이 답한 글자를 문서에서 **모두** 찾아 시작·끝 위치를 붙임 | LLM은 "몇 번째 글자"를 정확히 못 셈. 채점기는 위치가 필요함 |
| └ 이름 | 3글자 이름은 붙여 쓴 모양과 띄어 쓴 모양을 함께 찾음 (`이영희` ↔ `이 영희`), 앞이 한글이면 안 찾음 (`김은영` 안의 `은영` 방지) | |
| └ 겹침 | 찾은 위치가 겹치면 긴 것을 남김 | |

> 주의: "모두 찾기"와 "띄어 쓴 모양도 찾기" 때문에, LLM이 한 번만 답한 이름도 문서의 다른 위치까지 잡힙니다. 이건 LLM 탐지기 구현의 일부로 보고 모든 LLM 행에 똑같이 적용했습니다.

## 3. 후처리 1: 형식 정리 (`post_process`)

LLM 답 하나하나(`label`, `text`)에 아래 규칙을 **순서대로** 적용합니다.

| 순서 | 규칙 | 예 (LLM 답 → 결과) |
| --- | --- | --- |
| ① | **라벨 이름 통일**: 정해진 7종이 아닌 흔한 이름을 7종으로 바꿈 | `name`, `NAME`, `이름` → `person` / `phone`, `전화번호` → `phone_number` / `계좌번호` → `account_number` 등 |
| ② | **지어낸 라벨 처리**: 그래도 7종이 아니면, 사람을 뜻하는 말(`leader`, `manager`, `staff`, `customer`, `담당`, `직원`, `고객`, `팀장`, `성명` 등)이 들어 있으면 `person`, 아니면 **버림** | `team_leader` → `person` / `occupation`(직업), `date` → 버림 |
| ③ | **숫자 라벨 확인**: 전화·주민번호·계좌·카드 라벨인데 값에 숫자가 하나도 없으면 라벨 실수. 한글 이름 모양이면 `person`, 아니면 버림 | `노성호`(주민번호 라벨) → `person` |
| ④ | **소속 떼기** (이름만): 앞에 `○○팀`, `○○센터`, `○○본부`, `○○지점`, `○○부서`가 붙어 있으면 뗌 | `채권관리팀 이상훈` → `이상훈` |
| ⑤ | **직함·호칭 떼기** (이름만): 끝에 아래 말이 붙어 있으면 반복해서 뗌 — `고객(님)`, `팀장(님)`, `부장(님)`, `과장(님)`, `차장(님)`, `대리(님)`, `사원`, `주임`, `선임`, `책임`, `매니저`, `이사`, `대표`, `실장`, `본부장`, `지점장`, `상담원`, `님`, `씨` | `이준우 사원` → `이준우` / `민준씨` → `민준` / `남성호부장님` → `남성호` |
| ⑥ | **성+직함만 버리기** (이름만): 떼고 나서 한 글자 이하만 남으면 이름이 아님 → 버림 | `김 대리` → `김` → 버림 / `정` → 버림 |

**효과 (test, 형식 정리 전 → 후)**

| 모델 | strict P | strict R | 미끼 오탐 |
| --- | --- | --- | --- |
| HCX-007 | 0.934 → 0.984 | 0.950 → 0.972 | 11 → 3 |
| gpt-4.1-mini | 0.984 → 1.000 | 0.981 → 0.981 | 7 → 0 |
| gpt-5.4-mini | 0.967 → 0.996 | 0.995 → 0.998 | 9 → 4 |
| gpt-5.5 | 1.000 → 1.000 | 0.989 → 0.989 | 0 → 0 (고칠 게 없었음) |

## 4. 후처리 2: 하이브리드 후처리 (`keep`)

> ⚠️ 후처리 2는 test 오탐(`새봄카드` 등)을 먼저 본 뒤 만든 규칙이라, **보고서의 결과 표에서는 쓰지 않는다** (2026-10-23 결정). 정의는 기록으로 남긴다.

하이브리드는 아래 순서로 만듭니다.

```
① 규칙 v4가 찾은 것                         → 전부 그대로 둠
② LLM(형식 정리 후)이 찾은 것 중
   규칙 v4가 찾은 것과 겹치지 않는 것        → "더할 후보"
③ 후보마다 후처리 2 규칙 검사                → 하나라도 걸리면 버림
④ 남은 후보를 ①에 더함                      → 최종 결과
```

후보(LLM이 새로 더하려는 것)에 적용하는 규칙:

| 대상 라벨 | 규칙 (하나라도 해당하면 버림) | 예 |
| --- | --- | --- |
| person | 끝이 회사·부서·창구 이름 꼴: `카드`, `은행`, `보안`, `시스템즈`, `솔루션`, `센터`, `팀`, `본부`, `지점`, `법인`, `회사`, `그룹`, `저축은행`, `캐피탈`, `보험` | `새봄카드`, `고객센터`, `미르보안` |
| person | 역할을 뜻하는 단어: `민원인`, `고객`, `고객님`, `담당자`, `상담원`, `본인`, `자녀` | `민원인` |
| person | 사람 이름 모양이 아님: 한글 2~4자, 또는 `성 이름`(1자 + 공백 + 2자)이 아니면 | `이관 일정 확정`, `전 임직원` |
| phone_number | 회사 대표번호 모양: `15xx`·`16xx`·`17xx`·`18xx` + 4자리 | `1599-0000` |
| 전화·주민번호·계좌·카드 | 값에 한글이 섞임 | `민원번호: 202687652255` |

**효과 (test, rules v4 + HCX-007)**: 후처리 2 전 정밀도 0.986·미끼 오탐 3 → 후 0.998·0. 재현율은 그대로(0.997) — **진짜 개인정보는 하나도 버리지 않았음.**

### 여러 LLM을 한꺼번에 합칠 때 (`tools/merge_rules_multi_llm.py`)
후처리 2 규칙은 같고, ②의 "더할 후보"를 고르는 방법만 다릅니다.
- **union**: LLM 중 **1개라도** 찾았으면 후보
- **vote**: LLM 중 **2개 이상이 같은 자리**를 찾았으면 후보

## 5. 비교표 이름과 포함된 단계

| 비교표 이름 | 기본 처리 | 후처리 1 (형식 정리) | 규칙 v4 합치기 | 후처리 2 |
| --- | --- | --- | --- | --- |
| `llm ○○ (프롬프트만)` | ✅ | | | |
| `llm ○○ + 형식 정리` | ✅ | ✅ | | |
| `hybrid: rules v4 + ○○ + 후처리` | ✅ | ✅ | ✅ | ✅ |
| `hybrid_union` / `hybrid_vote` | ✅ | ✅ | ✅ (LLM 여러 개) | ✅ |

## 6. 팀 비교표와 맞출 때

팀 표의 `llm (프롬프트만 변경)`, `llm (프롬프트 + 규칙)`은 우리의 `(프롬프트만)`, `+ 형식 정리`와 **비슷한 개념이지만, 같은 규칙인지는 확인이 필요합니다.** 표를 합치기 전에 아래를 팀과 맞추세요.

1. "규칙"이 형식 정리(모양 바로잡기)만인지, 오탐 버리기(후처리 2 같은 것)까지인지
2. 위치 찾기 방식 (모든 등장 위치를 잡는지, 띄어 쓴 모양도 찾는지)
3. 규칙을 dev로만 만들었는지

---

## 7. 한계와 위험

- 후처리 규칙은 **dev에 나온 오류를 보고** 만들었습니다. holdout에 다른 모양의 오류(예: 끝 글자 규칙에 안 걸리는 회사명 `코드브릿지`)가 나오면 못 거릅니다.
- 반대로 이름이 우연히 `○○팀`, `○○센터`로 끝나거나 4자를 넘으면 진짜 이름을 버릴 수 있습니다. 개인정보 탐지에서는 버리기가 "놓치기" 위험이므로, 규칙은 **확실한 것만** 넣었습니다.
- 후처리 2는 LLM이 새로 더한 것에만 적용하므로, 아무리 잘못 걸러도 **최악의 경우 규칙 v4 단독과 같아집니다.**
