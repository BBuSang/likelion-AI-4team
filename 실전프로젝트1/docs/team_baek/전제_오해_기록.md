# 전제 오해 기록: "누구의 개인정보를 잡는가"

> Claude가 프로젝트 전제를 잘못 이해하고 진행한 내용을 따로 기록합니다. (2026-10-23)

---

## 1. 무엇을 잘못 이해했나

| | Claude가 이해한 전제 | 팀의 실제 기준 |
| --- | --- | --- |
| 잡아야 할 개인정보 | **사람 모두** (고객 + 직원 + 외부인) | **고객의 개인정보** |
| 성능 기준 | 제공 채점기(`run_compare.py`)의 전체 정답 1,165개 기준 | **고객 개인정보를 얼마나 잘 잡느냐** (test 고객 개인정보 458개) |
| 직원 이름을 잡으면 | 정답 | 틀린 것으로 치지 않음 (더 가린 것일 뿐) |
| 직원 이름을 놓치면 | 미탐 (성능 하락) | 성능과 무관 |

## 2. 왜 그렇게 이해했나

- 과제 설명의 첫 예시(D0002)에서 `상담원: 김은영`(직원)을 `person`으로 잡도록 되어 있었음
- 데이터의 정답 라벨에 직원·외부인 이름이 모두 들어 있음 (test 정답 1,165개 중 707개, 61%)
- 제공 채점기는 정답 전체를 기준으로 채점함

→ 이것만 보고 "모든 사람의 개인정보"를 기준으로 삼았고, **성능 기준을 사용자·팀에 먼저 확인하지 않았음.** 이것이 실수였다.

## 3. 오해 때문에 생긴 일

### 3-1. 직원 이름을 잡으려고 들인 노력
| 작업 | 내용 | 고객 기준에서 보면 |
| --- | --- | --- |
| 규칙 v2~v4 | 메신저 화자, 회의 참석자, `대표이사 ○○○`, `○○ 씨` 같은 규칙 다수 | 상당 부분이 **직원 이름**을 위한 규칙 |
| "규칙의 약점" 분석 | 놓친 13개(`은영이랑` 등)를 규칙의 유일한 약점으로 봄 | 13개 **전부 직원 이름** → 고객 기준으로는 약점이 아니었음 |
| rules v5 (문서 묶음 이름 사전) | 위 13개를 잡으려고 만듦 | 고객 기준으로는 **필요 없는 작업** |
| 하이브리드 (규칙 + LLM) | 규칙이 놓친 13개를 LLM이 메운다고 결론 | 고객 기준으로는 규칙만으로 이미 재현율 1.000 → **합칠 이유가 없음** |
| LLM 지시문 | "직원 이름도 모두 개인정보"라고 강조 | 고객 기준과 다른 지시 |

### 3-2. 잘못된 판단
- **DASH-002 평가**: "직원 이름을 개인정보로 안 봐서 틀렸다"고 설명했음. 고객 기준으로는 직원 이름을 안 잡은 것 자체는 문제가 아님. (다만 DASH는 고객 개인정보도 78개를 놓쳤으므로, 고객 기준으로도 성능이 낮다는 결론은 같음)
- **사용자에게 한 설명**: "고객뿐 아니라 직원까지 사람 모두의 개인정보를 잡는 것"이라고 단정적으로 설명했음. 데이터 정답의 기준을 설명한 것이지만, 팀의 성능 기준과 달랐음
- **결론의 순서**: "규칙 v4는 13개를 놓치므로 LLM과 합치면 더 좋다"를 주요 결론처럼 제시했음

### 3-3. 그대로 유효한 것
- 숫자형(전화·주민번호·계좌·카드)·이메일·주소 탐지 결과: 고객 정보 대부분이 여기에 해당하며, 결과는 그대로 유효
- 미끼 오탐 분석 (`정 부장`, `1599-0000` 등): 그대로 유효
- LLM의 일관성·속도·외부 전송 문제: 그대로 유효
- 전체 기준 결과표는 **제공 채점기 기준의 참고 자료**로 남김
