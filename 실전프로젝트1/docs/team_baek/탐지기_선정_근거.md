## 2. 무엇을 기준으로 골랐나

과제 원칙: **"하나 놓치는 것이 하나 더 가리는 것보다 훨씬 비싸다."** 그래서 F1 하나로 순위를 매기지 않고 아래 순서로 봤습니다.

| 순위 | 기준 | 지표 | 왜 중요한가 |
| --- | --- | --- | --- |
| 1 | 안 새어 나가기 | **mask_rec**, 재현율 | 놓친 개인정보는 벡터 DB·LLM 로그로 그대로 흘러감 |
| 2 | 운영 가능성 | **원문 외부 전송 여부** | 개인정보를 찾으려고 원문을 클라우드에 보내면 모순 |
| 3 | 속도 | ms/문서 (CPU) | 운영 환경은 GPU 없는 CPU 서버. 문서가 계속 쌓임 |
| 4 | 일관성 | 3회 실행 시 결과가 같은 문서 비율 | 같은 문서가 어떤 날은 가려지고 어떤 날은 안 가려지면 안 됨 |
| 5 | 정밀도 | strict P, 미끼 문서 오탐 | 너무 많이 가리면 검색·분석 품질이 떨어짐 |

## 4. 방식별 강점과 약점

### rules v4 (규칙 기반)
- **강점**
  - 숫자형 5종(전화·이메일·주민번호·계좌·카드)과 주소는 test에서 **100%**
  - 대표번호(`1599-0000`), 상품명(`한결 플러스 카드`), 12자리 민원번호 같은 **미끼에 한 번도 안 속음**
  - 같은 문서는 몇 번을 돌려도 결과가 같음
  - CPU에서 문서당 0.5ms, 외부 전송 없음
- **약점**
  - **문맥 단서 없는 이름**에 약함: 놓친 13개가 모두 메신저의 `은영이랑`처럼 성 없이 처음 나오는 이름 (성 없는 이름 재현율 0.705)
  - dev·test에 있는 문장 틀에 기댄 규칙이 있음 — 특히 메신저 규칙은 한 가지 문서 틀에서만 작동 (옛 rules v3 진단 기록, git에는 올리지 않음)
  - 처음 보는 표기에 대비해 v4에서 넓혔지만(직접 만든 예문 3/27 → 26/27), holdout에서 확인 필요

### LLM 단독
- **강점**
  - 문맥을 이해해서 **성 없는 이름**을 잘 잡음 (gpt-5.4-mini 재현율 0.998)
  - 규칙을 따로 만들지 않아도 처음 보는 문장에 어느 정도 대응
- **약점**
  - 모델마다 **엉뚱한 판단**: gpt-5.5는 메일 서명의 02 회사 직통번호 13개를 모두 "개인정보 아님"으로 뺌. DASH-002는 회의록·메신저 32건을 통째로 "개인정보 없음"
  - 지시를 정확히 안 따름: 회사 이름(`새봄카드`)·`고객센터`를 사람으로, 성 한 글자(`정`)를 이름으로 → **형식 정리 단계가 꼭 필요**
  - temperature를 낮춰도 **실행마다 결과가 달라짐** (HCX-007 문서의 14%)
  - 규칙보다 **약 2,500~12,000배 느림**, API 요청 한도에 묶임
  - **원문을 클라우드로 보내야 함** (아래 5번)

### 하이브리드 (rules v4 + LLM, 후처리 없이 합침)
- 규칙과 LLM의 **약점이 겹치지 않음**: 규칙이 놓친 13개를 LLM이 모두 잡고, LLM이 놓친 02 번호 등은 규칙이 모두 잡음. **둘 다 놓친 것 0개**
- 후처리 없이 합쳐도 재현율·mask_rec 1.000. 다만 LLM의 오탐이 그대로 들어옴 (gpt-4.1-mini 합치면 성 한 글자 `정` 등 19개). gpt-5.5는 원래 오탐이 없어 합쳐도 오류 0
- 속도·외부 전송 문제는 LLM 단독과 같음

## 5. 왜 LLM을 기본으로 쓰지 않나 — "원문을 밖으로 보내는 모순"

LLM 탐지는 **개인정보가 들어 있는 원문을 그대로** 클라우드 API에 보내야 합니다. 이번 실험은 가상 데이터라 허용됐지만, 실제 고객 문서라면:

- 개인정보를 보호하려고 만든 시스템이, 탐지 단계에서 개인정보를 외부 업체로 보내게 됨
- 금융사 내부 규정·개인정보보호법상 외부 전송 자체가 문제가 될 수 있음
- 규칙으로 먼저 가린 뒤 남은 텍스트만 보내도, **규칙이 놓친 이름(=LLM이 찾아야 할 것)은 그대로 전송됨**

**LLM을 운영에 쓰려면 필요한 형태**
1. **내부망(온프레미스)에서 도는 LLM** — 원문이 회사 밖으로 나가지 않음. 단, CPU 서버에서는 느리므로 작은 모델이나 별도 서버가 필요
2. 외부 API를 쓴다면 **개인정보를 보내지 않는다는 계약·설정**(데이터 학습·저장 안 함)과 법무 검토
3. 모든 문서가 아니라 **규칙이 약한 문서·문장에만** LLM을 쓰도록 범위를 줄이기

| 단계 | 탐지기 | 이유 |

## 7. 한계 (정직하게)

- **가상 데이터**: 템플릿에 값을 채워 만든 문서라 실제 문서보다 깨끗하고 규칙적임
- **dev와 test가 같은 문서 틀**(23종)을 씀: test 점수가 "처음 보는 문서"에서의 성능을 보장하지 않음 → **holdout(새 템플릿 16종) 최종 평가 필요**
- 규칙·프롬프트·형식 정리(후처리 ①)는 **dev를 보고 만들었음**. test를 먼저 보고 만든 것(rules v5, 하이브리드 후처리 ②)은 결과에서 뺐음
- 하이브리드의 test 만점은 이 200건에서의 결과일 뿐
- 토큰 분류 모델(팀원 담당) 결과가 아직 비교에 들어가지 않음
- LLM 속도는 API 상황(요청 한도·네트워크)에 따라 달라짐
