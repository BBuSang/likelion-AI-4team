## 1. 성능 기준을 잘못 이해함 (가장 큰 문제)

**무슨 일이 있었나**
- AI는 과제 예시(`상담원: 김은영`을 개인정보로 표시)와 데이터 정답(직원 이름 포함)을 보고, **"고객·직원 모두의 개인정보를 잡는 것"**으로 판단하고 진행했습니다. 성능 기준을 저에게 먼저 확인하지 않았습니다.
- 제가 "고객 정보만 잡으면 된다"고 말했을 때도, AI는 처음에 "직원도 개인정보라 잡아야 한다"고 설명했습니다.

**영향**
- 규칙 기반이 놓친 13개(메신저의 `은영이랑` 등)를 "규칙의 약점"으로 보고, 이를 메우려고 v5(문서 묶음 이름 사전)와 LLM 하이브리드를 만들었습니다. 확인해 보니 **13개 모두 직원 이름**이었습니다.
- "규칙에 LLM을 합치면 더 좋다"를 주요 결론처럼 제시했습니다.

**조치**
- 고객 기준 채점 도구를 새로 만들었습니다 (`tools/eval_customer.py`, 정답의 역할 `C` = 고객만 채점).
- **고객 기준 결과: 규칙 기반 v4가 test 고객 개인정보 458개를 하나도 놓치지 않음** (재현율·mask_rec 1.000, 오탐 0, 문서당 0.5ms). → 고객 기준에서는 LLM을 합칠 이유가 없음.
- 팀 기준을 `CLAUDE.md`(AI가 매번 읽는 규칙 파일)에 적어, 다시 같은 실수를 하지 않도록 했습니다.
  - 필요한 것은 고객 정보를 가리는 것뿐
  - 직원 관련(직원 이름, `정 부장`처럼 성+직함)은 잡든 안 잡든 상관없음
  - 직원 이름을 놓친 것은 미탐으로 세지 않음

## 2. test 오류를 본 뒤 규칙을 만들어 점수가 부풀려짐

**무슨 일이 있었나**
- AI가 중간 점검에서 **test 오류 목록을 먼저 본 뒤**, 그 유형을 겨냥한 규칙(v5)과 LLM 후처리 규칙을 만들었습니다. 그 결과 test 점수가 1.000이 나왔고, 처음엔 좋은 결과처럼 보고했습니다.
- 제가 "왜 1이 나오냐, 수상하다"고 묻자, AI가 이 사실을 인정했습니다. (정답 파일이나 인물 목록을 몰래 본 것은 아님)

**조치**
- 해당 점수(v5, 후처리)는 **"낙관적인 참고 점수"**로 분류하고 보고서에 밝히기로 했습니다.
- **이전 규칙 코드를 쓰지 않고 규칙을 처음부터 새로 만들어(rules clean)** test 숫자만 확인 → **v4와 완전히 같은 점수**. v4의 점수는 test를 본 영향 없이 나온 믿을 수 있는 숫자임을 확인했습니다.
- 실전 1의 최종 규칙 탐지기는 **v4로 고정**했습니다. v5는 종합 단계의 holdout에서 함께 검증할 후보로 남깁니다.
- AI 규칙 파일에 "test 오류 목록은 꼭 필요할 때만 보고, 본 오류를 겨냥한 규칙의 점수는 낙관적이라고 밝힌다"를 추가했습니다.

## 3. "후처리" 용어 혼란

**무슨 일이 있었나**
- AI가 LLM 결과를 고치는 단계를 "거르기", "형식 정리", "후처리" 등 여러 이름으로 불러, 표에서 어떤 결과에 무엇이 들어갔는지 헷갈렸습니다.

**조치**
- `docs/후처리_정의.md`에 정의를 정리했습니다. 후처리는 두 가지입니다.
  - ① 형식 정리: LLM 답의 모양을 바로잡음 (라벨 이름, 직함 떼기)
  - ② 하이브리드 후처리: 규칙과 LLM을 합칠 때 회사명·대표번호 등을 버림
- 비교의 공정성을 위해 **대표 결과는 후처리를 모두 뺀 결과**로 정리했습니다.

## 4. 할루시네이션(지어낸 답) 우려

**무슨 일이 있었나**
- AI가 데이터의 역할 코드 `C`를 "고객"이라고 했는데, 이는 설명서를 본 것이 아니라 **추론**이었습니다. 이 밖에도 추론을 확정처럼 말한 적이 있었습니다.

**조치 (검증)**
- 역할 코드 확인: `C`인 사람은 앞에 `고객:`·`민원인:`·`성명:`, 뒤에 `고객`·`님`이 붙음. 주민번호·계좌·카드·주소의 주인은 100% `C` → **C = 고객 확인**
- AI가 만든 채점 도구를 쓰지 않고 **처음부터 다시 계산** → 같은 결과
- 문서에 옮겨 적은 표를 도구 출력과 **한 줄씩 대조** → 일치
- **제가 직접 오류 파일을 열어** 규칙 기반이 놓친 13개가 메신저 속 직원 이름임을 확인했습니다.

## 5. 설명이 너무 길고 어려움

- 초보 입장에서 AI의 설명이 길고 용어가 많아 이해가 어려웠습니다. "더 쉽게", "원래 의미가 뭐냐"고 여러 번 요청해 비유와 표로 다시 설명받았습니다.
- AI 규칙 파일에 "사용자는 초보이므로 쉬운 말로 쓴다"를 넣었습니다.

## 6. 담당 범위 (팀 조율 필요)

- 저는 규칙 기반 담당이지만, AI와 함께 **LLM 탐지(HCX-007, DASH-002, GPT 3종)와 하이브리드 실험**까지 진행했습니다.
- LLM 담당 팀원과 결과가 겹치거나 기준이 다를 수 있어, 공유와 조율이 필요합니다.

## 팀장님께 확인·결정 부탁드릴 것

1. **성능 기준**: "고객 정보를 빠짐없이 가렸는가(고객 재현율·mask_rec)"를 팀 공식 기준으로 해도 될지
2. **팀 비교표의 `rules` 행**(P 0.997 / R 0.996): 제 결과(전체 기준 P 1.000 / R 0.989, 고객 기준 1.000)와 다릅니다. 어느 버전·어느 데이터로 잰 것인지 확인 부탁드립니다
3. **LLM 실험 결과 공유 방법**: LLM 담당과 결과·기준을 어떻게 합칠지
4. **고객/직원 구분**: 종합 단계의 권한 기능을 위해, 탐지기가 고객과 직원을 구분하는 능력도 평가할지

## 현재 결론

> **실전 1 규칙 기반 최종 탐지기 = rules v4.**
> 고객 기준으로 test 고객 개인정보 458개를 모두 잡았고, 오탐 0, 문서당 0.5ms, 결과가 항상 같고, 원문을 외부로 보내지 않습니다.
> 단, 가상 데이터이고 dev와 test가 같은 문서 틀이라 **최종 성능은 holdout으로 확인**해야 합니다.
