### 데이터 관찰 메모
- 라벨은 **7종**. 노션에는 8종이라고 했지만 organization 정답은 0개이고 채점기도 7종만 채점함
- person이 62%(340/548)로 압도적이라 **이름 탐지가 성패를 좌우함**
- 전화번호 형식 7가지: `010-0000-0000`, `01000000000`, `010.0000.0000`, `010 0000 0000`, `02-0000-0000`(지역번호) 등
- 정답 기준(README가 없어 데이터에서 추론):
  - 성+직함(`허 부장님`)은 개인정보 아님 (`surname_title_unlabeled` 태그)
  - 이름만 쓴 경우(`소율 씨`)는 개인정보임
  - 조사는 빼고 이름만, 주소는 `, 15층`·`101동 1202호`까지 포함
  - 대표번호(`1599-0000`), 민원번호(`202611910266`), 날짜는 개인정보 아님
- 채점기 해석 주의점: 윈도우에서 출력을 파일로 넘기면 `⚠` 문자 때문에 멈춤 → `python -X utf8`로 실행. 어려운 사례 표는 "그 태그가 있는 문서의 이름 전체" 재현율이라, 띄어 쓴/이름만 쓴 경우는 `[추가] person form=` 줄을 볼 것

## 3. 작업 과정 (시간순)

### 3-1. 규칙 기반 (dev에서 3번 개선)

| 버전 | 변경 | strict F1 | mask_rec | 결과 폴더 |
|---|---|---|---|---|
| v1 | 정규식(이메일·주민·카드·전화·계좌·주소) + Kiwi NNP & 성씨 + 띄어 쓴 이름·`OO 씨`·`OO아,` 규칙 | 0.831 | 0.962 | `results/dev_rules_v1` |
| v2 | ① 날짜를 계좌에서 제외 ② 이름 판단을 "붙어 있는 명사 조각을 합친 3글자 덩어리"로 변경 | 0.843 | 0.991 | `results/dev_rules_v2` |
| v3 | ③ 사전에 있는 일반명사 한 단어(`서비스`, `임직원`)는 이름에서 제외 | **0.956** | **0.990** | `results/dev_rules_v3` |

발견한 것
- **v1 계좌번호 오탐 61건은 전부 날짜**였음(`2026-06-25`가 `숫자-숫자-숫자` 모양). → 연-월-일 모양 제외
- **Kiwi는 이름을 잘 모름.** `최채원`은 사전에 없는 단어(OOV, id=2)로, `신승현`은 `신승+현`으로, `남성호`는 `남성+호`로 쪼갬. "고유명사(NNP)인가"로는 이름의 절반가량을 놓침
- v2에서 재현율은 0.97로 올랐지만 `서비스`·`연락처`·`임직원`처럼 **성씨 글자로 시작하는 일반 단어** 184건을 오탐
- 해결: Kiwi가 아는 일반명사는 **한 조각 + 사전 id**로 나오고, 이름은 **OOV이거나 여러 조각으로 쪼개짐** → 이 차이로 구분
- 남은 오류(dev 기준 개선 중단): `정은영님은` 같은 쪼개짐 차이, `인사팀`·`연회비`·`고객명` 오탐. 더 고치면 dev에만 맞춰질 것 같아 멈춤

### 3-2. 토큰 분류 모델 2종

| 모델 | 라이선스 | 크기 | 라벨 대응 |
|---|---|---|---|
| `atonlee/koelectra-ko-pii-ner` | Apache-2.0 | 14M | 7종 모두 있음. ORGANIZATION·DATE·POSITION 등은 버림 |
| `ParkJunSeong/PIILOT_NER_Model` | Apache-2.0 | 112M | **card_number 없음** (카드번호를 account로 잡음) |

> 학습 데이터·모델 카드 자체 벤치마크 점수는 아직 확인하지 않았어요 → 보고서에 넣으려면 모델 카드 확인 필요 (아래 6장)

- 문서를 **줄 단위**로 넣음: 512토큰 초과를 막고, 줄을 넘어 두 이름이 한 덩어리로 합쳐지는 문제를 막기 위해
- **aggregation 설정 비교** (서브워드 조각을 개체로 묶는 방식, `results/dev_aggregation_test`)

| | simple (조각 단위) | first (단어 단위) | 선택 |
|---|---|---|---|
| KoELECTRA strict F1 | **0.911** | 0.812 | simple |
| PIILOT strict F1 | 0.173 | **0.612** | first |

  - PIILOT은 simple이면 `김은영`을 `김은`+`영`으로 쪼갬. first는 단어 단위로 묶어서 해결
  - KoELECTRA는 first면 `윤선영은`처럼 조사까지 붙여서 오히려 나빠짐
  - → **모델별로 dev에서 더 나은 설정을 골랐어요** (보고서에 명시할 것)

### 3-3. LLM (gpt-4.1-mini, temperature 0, JSON 출력, 8개 병렬 호출)

- 모델 선택 이유: 저렴·빠름, temperature 조절 가능(GPT-5 계열 추론 모델은 불가) → 일관성 실험에 적합
- LLM에게는 **값 + 라벨만** 받고 위치는 코드가 원문에서 찾음(LLM은 글자 위치를 정확히 못 셈)

| 버전 | 변경 | strict F1 | 이름 재현율 | mask_rec |
|---|---|---|---|---|
| v1 | 기본 프롬프트 (라벨 정의 + 제외 기준) | 0.894 | 0.715 | 0.922 |
| v2 | ① "직원·협력사 직원 이름도 포함" ② "표기가 다르면 각각 적기, 애매하면 포함" ③ 이름은 띄어쓰기 무시하고 원문에서 모두 찾기 | **0.982** | **0.956** | **0.985** |

발견한 것
- v1은 **상담원·팀장 같은 직원 이름을 개인정보가 아니라고 판단**해서 빠뜨림 (예: `상담원: 김은영`)
- v1은 `윤 선영`만 답하면 같은 사람의 `윤선영`을 못 찾음 → 이름은 공백 무시 검색으로 해결
- `소율`이 `이소율` 안에서 잡히지 않도록, 앞 글자가 한글이면 매칭하지 않게 함
- 일관성(3회 실행): v1 문서 93% 동일, v2 92% 동일 (평균 Jaccard 0.99) → **temperature 0이어도 결과가 완전히 같지는 않음**

### 3-4. 합집합 (노션 "정규식 보강 결과와 합집합")
- `make_union.py`: 위치가 겹치면 앞 파일(규칙)을 우선, 처리 시간은 두 탐지기 합
- 규칙 + KoELECTRA, 규칙 + LLM 두 조합을 만듦

### 3-5. test 최종 채점 (한 번만 실행, `results/test_final`)
모든 설정을 dev에서 확정한 뒤 test를 처음 열어 채점했어요.

## 4. 결과

### 4-1. 전체 성능 (test 200건, 정답 1,165개)

| 시스템 | strict P | strict R | strict F1 | partial F1 | **mask_rec** | ms/문서 | 1만 건 처리 |
|---|---|---|---|---|---|---|---|
| 규칙 기반 | 0.955 | 0.953 | 0.954 | 0.957 | 0.984 | **3.9** | 약 40초 |
| KoELECTRA | 0.866 | 0.956 | 0.909 | 0.943 | 0.987 | 240 | 약 40분 |
| PIILOT | 0.599 | 0.677 | 0.636 | 0.867 | 0.807 | 491 | 약 82분 |
| LLM | **0.991** | 0.953 | **0.972** | **0.975** | 0.973 | 1,425 | 약 4시간 (8개 병렬 시 약 30분) |
| **규칙 + KoELECTRA** | 0.874 | **0.995** | 0.931 | 0.935 | **1.000** | 244 | 약 41분 |
| 규칙 + LLM | 0.952 | 0.990 | 0.971 | 0.974 | 0.998 | 1,429 | 약 4시간 |

- 1만 건 처리 시간 = 문서당 시간 × 10,000 (순차 처리 기준)
- 오차 범위: 정답 1,165개라 전체 지표는 대략 **±2%p**. 규칙(0.954)과 LLM(0.972)의 F1 차이 1.8%p는 **"비슷하다"에 가까움**

### 4-2. dev → test 변화 (과적합 점검)

| 시스템 | dev strict F1 | test strict F1 | 변화 |
|---|---|---|---|
| 규칙 기반 | 0.956 | 0.954 | -0.002 |
| KoELECTRA | 0.911 | 0.909 | -0.002 |
| PIILOT | 0.612 | 0.636 | +0.024 |
| LLM | 0.982 | 0.972 | -0.010 |

전체 점수는 거의 그대로지만, **규칙 기반의 이름만 쓴 경우(given) 재현율은 0.867 → 0.750으로 떨어짐.** dev 문맥(`OO 씨`, `OO아,`)에 맞춘 규칙이 새 문맥에서 통하지 않은 것 → dev 과적합의 실제 사례.
다만 test는 dev와 같은 템플릿 23종을 써서, 처음 보는 형식의 문서(holdout)에서는 더 떨어질 수 있음.

### 7-0. 사전 조사에서 확인한 것

### 7-2. ④ 규칙 기반 이름 규칙 일반화 (`detectors/rule_based.py`)
1. `님`·`씨`(NNB)는 명사 덩어리에 붙이지 않음 → `노성호님`이 4글자가 되어 빠지던 문제 해결
2. **3글자 + 님/씨/직급** 규칙 추가 (`신승현 과장`, `신현준 매니저`)
3. 명사+접미사 덩어리(`인사팀`, `고객명`, `연회비`)와 기관 이름 앞부분(`하늘빛은행`)은 이름에서 제외

- 첫 시도에서 직급 목록에 `고객`·`지점`까지 넣었더니 `문의는 고객센터`의 `문의는`, `여의도지점`의 `여의도`를 이름으로 오탐 → **실제 직급만** 허용하도록 좁힘
- `연회비`는 Kiwi가 문맥마다 다르게 쪼개서 "마지막 조각"이 아니라 **마지막 글자**로 접미사 판단

차이 원인 추정 (노션 질문 "모델 카드 점수와 우리 점수가 왜 다른가")
- KoELECTRA는 **금융 PII 데이터로 학습**해서 우리 금융 문서와 분야가 맞고, 평가 방법(boundary/type)도 자세히 공개됨
- PIILOT은 평가 데이터가 공개되지 않았고, 서브워드 경계 문제(`김은`+`영`)·라벨 혼동(휴대폰→주민번호)이 커서 **다른 분포의 데이터로 잰 점수**로 보임
- 교훈: 모델 카드 점수는 **제작자 데이터 기준**이라, 반드시 우리 데이터로 다시 재야 함

| 규칙 v3 | 0.914 | 0.944 | 0.998 | 0.986 | 0.994 | 0.750 |

### 9-3. 형태소 분석기 비교 (`detectors/analyzers.py`, `compare_analyzers.py`)

**방법**
- 규칙은 그대로 두고 **분석기만 교체**: Kiwi(0.24.1), KoNLPy의 Komoran·Kkma·Hannanum·Okt (Java 21)
- Mecab은 Python 3.13용 윈도우 설치 파일이 없어 제외
- 분석기 출력을 같은 모양(조각·세종 품사·원문 위치·사전 밖 단어 여부)으로 맞추는 어댑터를 만듦. Kiwi만 원문 위치를 주고, 나머지는 조각을 원문에서 순서대로 찾아 붙임 (`했`→`하+았`처럼 바뀐 조각은 버림)
- 사전 밖 단어 정보: Kiwi(OOV id), Komoran(NA 태그), Kkma(UN 태그)만 있음. Hannanum·Okt는 없음
- 설정 2개: **full**(실제 사용 설정) / **core**(문맥 규칙 끔 = 분석기의 명사 덩어리 판단만)

**같은 단어를 분석기마다 어떻게 쪼개나** (노션 질문)

| 입력 | Kiwi | Komoran | Kkma | Hannanum | Okt |
|---|---|---|---|---|---|
| 윤선영은 | 윤/NNP 선영/NNG 은/JX | 윤선/NNP 영/NNP 은/JX | 윤/NNG 선영/NNG 은/JX | 윤선영/NC 은/JX | **윤선/Noun 영은/Noun** |
| 신승현 과장 | 신승/NNG 현/MM 과장 | **신승현/NNP** 과장 | 신승/NNG (+혀/ㄴ 동사로 오분석) | 신승현/NC 과장 | 신승현/Noun 과장 |
| 손하은 책임 | 손/NNG 하/XSV 은/EC | 손/NNG 하/XSV 은/ETM | 손/NNG **하은/NNP** | 손하/NC 은/JX | 손하은/Noun |
| 최채원 고객은 | **최채원/NNG(사전 밖)** | 최/NNP 채원/NNP | 최/NNP 채원/NNG | 최채원/NC | 최/Noun 채원/Noun |
| 남궁다은 | **남궁다은(사전 밖)** | 남궁/NNP 다/JX 은/JX | 남궁/NNG 다/MAG 은/NNG | 남궁다/NC 은/JX | 남궁/Noun 다/MAG 은/Noun |
| 배송지 | 배송지/NNP | 배송지/NNP | 배송/NNG | 배송지/NC | 배송지/Noun |
| 한결 플러스 카드 | 한결/MAG 플러스 카드 | 한결/MAG 플러스/NNP 카드 | 한결/MAG … | 한결/MAG … | 한결/Noun … |

→ 어떤 분석기도 이름을 일관되게 다루지 못함. **차이는 "이름을 모를 때 어떻게 표시하느냐"**에서 남

**성능** (`results/analyzer_comparison.csv`, 이름은 partial 기준)

| 분석기 | test strict F1 | test mask_rec | test 이름 R | test 이름 P | 엣지 mask_rec | dev ms/문서 |
|---|---|---|---|---|---|---|
| **Kiwi** | **0.991** | **0.997** | **0.985** | 0.999 | **1.000** | **6.7** |
| Komoran | 0.933 | 0.963 | 0.849 | 0.956 | 0.993 | 8.1 |
| Kkma | 0.911 | 0.944 | 0.774 | 0.979 | 0.987 | 727 |
| Hannanum | 0.602 | 0.787 | 0.147 | 1.000 | 0.948 | 2.3 |
| Okt | 0.612 | 0.802 | 0.206 | 0.681 | 0.956 | 1,834 (첫 실행 포함) |

core 설정 (문맥 규칙 끔, 분석기만으로 이름 찾기), test 이름 재현율: Kiwi 0.837 · Komoran 0.591 · Kkma 0.409 · Okt 0.031 · Hannanum 0.000

**해석**
1. **Kiwi가 가장 좋음.** 핵심은 **"사전 밖 단어(OOV)" 표시**. 이름은 대부분 사전에 없어서 이 정보로 `서비스`(사전 단어) vs `최채원`(사전 밖)을 구분함
2. **Komoran**은 이름을 NNP로 잘 붙이지만 `최/NNP 채원/NNP`처럼 쪼개고, `배송지`·`플러스`도 NNP라 정밀도가 떨어짐 → 2위
3. **Kkma**는 정확도는 3위지만 **문서당 0.5~0.8초**로 Kiwi의 100배 이상 느림 → 1만 건이면 약 2시간
4. **Hannanum·Okt**는 사전 밖 단어·고유명사 정보가 없어(모두 일반명사) 규칙이 이름을 "사전에 있는 일반 단어"로 보고 버림 → 이름 재현율이 0.15~0.21로 붕괴. 문맥 규칙(필드·호칭)이 잡은 것만 남음
5. **문맥 규칙의 가치**: full과 core의 차이가 분석기가 약할수록 큼. 문맥 규칙이 분석기의 약점을 메워 줌

**공정성 주의**
- 규칙(일반 단어 필터, 명사 덩어리 판단)을 **Kiwi로 dev에서 다듬었기 때문에** Kiwi에 유리한 비교임. 다른 분석기에 맞춰 규칙을 다시 다듬으면 격차가 줄 수 있음
- Hannanum은 짧은 단어 단위 호출에서 Java 예외를 자주 냄(문서 줄 단위 분석은 dev 904줄 중 실패 0건). 실패한 호출은 "분석 결과 없음"으로 처리
- Okt·Kkma의 처리 시간에는 JVM 호출 비용이 포함됨. 첫 실행 캐시 효과로 dev 수치가 test보다 크게 나옴

**결론: 규칙 기반은 Kiwi를 그대로 사용.** 보고서에는 "분석기 선택이 이름 탐지 재현율을 0.15~0.99로 바꿀 만큼 결정적이며, 핵심은 사전 밖 단어 정보"라고 쓸 수 있음

### 10-1. 질문: 이름이 '김우리', '김하나'면 은행으로 잡힐까?
**잡히지 않음** (v4에서 문장 8개로 확인)

| 문장 | 결과 |
|---|---|
| `고객 김하나 010-0482-7713` | 김하나 → 이름, 번호 → 전화 |
| `하나 김우리 01004827713` | 김우리 → 이름, 번호 → 전화 |
| `김하나 대리가 응대함. 하나은행 계좌 1002-…` | 김하나 → 이름, 번호 → 계좌 |
| `우리 김하나 님께 전달해 주세요` | 김하나만 이름 |

이유
- 은행 이름 규칙(`국민`, `하나`, `우리` …)은 **하이픈 없는 10~14자리 숫자 바로 앞**에서만 씀. 전화 모양은 전화 규칙이 먼저 잡고, `계좌`·`은행`·`입금` 같은 확실한 단어가 있을 때만 계좌로 바꿈
- 이름 퍼뜨리기는 `하나`, `우리`처럼 사전에 있는 단어를 "이름만 쓴 형태"로 퍼뜨리지 않음 → `하나 더`, `우리 팀`은 이름이 안 됨
- 참고: Kiwi는 `김하나님`을 `김 + 하나님`으로 분석하지만 호칭 규칙으로 이름이 잡힘

## 11. 일상 문서 2,000건 생성 + 규칙 v6 (2026-10-22)

### 11-1. 왜 만들었나
- 제공 데이터는 템플릿 23종이라 형식이 단조롭고, 엣지 케이스는 규칙 작성자가 써서 점수가 낙관적
- 팀 요청: 상담·환불처럼 **일상에서 쓰는 카테고리**로 대량 시험 데이터를 만들어 다시 시험
- 노션 제약("제공 데이터셋으로 한정")은 실제 개인정보 금지 취지로 보고, **추가 견고성 시험으로 따로 표기**. 멘토님께 알릴 것

### 11-2. 편향을 줄이는 방법
| 위험 | 대응 |
|---|---|
| 규칙 작성자가 규칙에 맞춰 문서를 씀 | **OpenAI gpt-4.1**이 작성 (작성자 ≠ 규칙 작성자) |
| 프롬프트에 규칙이 새어 들어감 | 프롬프트에는 카테고리·문체·라벨 표시 기준(데이터셋 정답 기준)만. 규칙·형식 목록은 넣지 않음 |
| 생성 결과를 보고 규칙을 맞춤 | **절반은 holdout**: 오류 목록을 열지 않고 점수만 봄 |
| 정답(표시) 오류 | 형식 검사 + 검수 후보 목록(`qc_synthetic.py`) |

- 프롬프트 전문: `generate_synthetic.py`의 `PROMPT`

## 12. 팀 라벨 기준 정리 + 장소 주소 제외 (v7, 2026-10-22)

### 12-1. 팀 라벨 기준 (보고서 ① 데이터 관찰 리포트의 "팀 라벨 기준"에 사용)
개인정보인지는 **"이 값으로 특정한 사람을 알아낼 수 있는가"**로 판단

| 표현 | 판단 | 이유 |
|---|---|---|
| `김 과장`, `허 부장님` (성 + 직함) | 개인정보 아님 | 한 사람으로 특정되지 않음 (데이터셋 `surname_title_unlabeled` 기준과 같음) |
| `소율 씨`, `승현아` (이름만) | 개인정보 | 문서 안에서 특정인을 가리킴 |
| 회사 대표번호 `1522-0800`, `1588-xxxx`, 080 | 개인정보 아님, **누구에게도 연결하지 않음** | 콜센터로 연결될 뿐 상담사·고객 누구도 특정하지 않음 |
| 직원 직통번호 `02-3961-1452` | 개인정보 (그 직원) | 한 사람에게 연결됨 |
| **장소 주소** (웨딩홀·장례식장·회식·모임·호텔 등) | **개인정보 아님** | 누구나 찾아가는 장소라 개인을 특정하지 않음 |
| 집 주소, 배송지, 등기 주소 | 개인정보 | |
| 동·호수가 있는 주소 (`902동 505호`) | **개인정보** (장소 문맥이어도) | 사는 집일 수 있음 (`직거래 … 902동 505호에서`) |
| 토스 등 휴대폰 번호 계좌 | 계좌 (`계좌`·`은행` 바로 뒤일 때) | 둘 다 가려지므로 mask_rec 영향 없음 |
| 일부를 가린 값 `900512-2******` | 개인정보 | 보이는 부분만으로도 일부 정보가 드러남 |
| 계좌 앞 은행 이름 | 범위 밖 (번호만) | 데이터셋 정답 기준과 같음 |

**장소 주소 판단은 비대칭**: 장소를 뜻하는 말(`장소:`, `식장`, `빈소`, `회식`, `모임`, `오시는 길`, `매장`, `본사`, `지점` …) 또는 주소 뒤 업장 이름(`웨딩홀`, `장례식장`, `호텔`, `카페` …)이 **확실히 있고**, 개인을 가리키는 말(`주소`, `거주`, `자택`, `집`, `배송`, `수령`, `변경`, `등기`, `임차` …)이 **없고**, **동·호수가 없을 때만** 뺀다. 문맥이 없으면 가린다 → 집 주소를 놓치는 것이 장소 주소를 가리는 것보다 훨씬 위험하기 때문

### 12-2. 구현 (`postprocess.drop_venue_addresses`)
- 규칙(`rule_based.py`)과 모델(`token_cls.py` 후처리) **양쪽에 같은 함수**를 붙여 합집합도 같은 기준을 따르게 함
- 처음에는 `직거래`를 장소 단어에 넣고 동·호수 조건이 없었음 → `직거래 … 902동 505호에서`, `장소: … 203호` 같은 집일 수 있는 주소까지 빼서 수정

### 15-4. 해석
1. **규칙 단독**: 가장 빠르고(문서당 2~5ms) 제공 데이터에서는 가장 정확하지만, 일상 문서에서 mask_rec이 0.972~0.977로 떨어짐 → 놓치는 개인정보가 2~3%
2. **토큰 단독**: 일상 문서에서는 규칙보다 놓치는 게 적지만(0.981~0.984), 엣지 케이스(안심번호·휴대폰 계좌·외국인등록번호 등)에서 0.921로 약하고 경계가 부정확해 strict F1이 가장 낮음
3. **규칙 + 토큰 (전체 합집합)**: **모든 데이터에서 mask_rec 최고** (제공 데이터·엣지 1.000, 일상 문서 0.987~0.988). 시간은 토큰 단독과 거의 같음(규칙이 매우 빠르기 때문) → **1만 건 약 5~9분, CPU만으로 충분**
4. **이름만 결합(팀원 방식)**: 정밀도·strict F1은 더 높지만, 규칙이 놓친 번호·주소를 모델이 잡아도 버려서 일상 문서 mask_rec이 0.976~0.982로 낮아짐 → 재현율 우선 기준에서는 **전체 합집합이 낫다**. 팀원 결론과 다른 이유: 팀원은 제공 데이터로만 비교했는데, 거기서는 규칙의 정형 라벨이 이미 완벽해서 두 방식의 차이가 드러나지 않음 (우리 dev·test에서도 두 방식 점수가 같음)

**결론: 운영 탐지기 = 규칙(v7, Kiwi) + atonlee(팀원 래퍼) 전체 합집합**
- 정밀도 하한선: 일상 문서 strict P 0.908~0.934 (오탐 상당수는 생성 정답의 표시 누락·장소 주소 기준 차이, 11-5·12장)

4. **일관성**: LLM은 모델에 따라 77.5~98.5% (같은 문서가 실행마다 다르게 가려짐 → 가명 토큰이 바뀔 위험). 규칙 + 토큰은 100%
5. **비용**: 문서마다 API 비용 발생. 규칙 + 토큰은 CPU만

**LLM 단독을 탈락시킨 이유**: 가장 좋은 모델(gpt-5.4-mini)도 mask_rec이 규칙 + 토큰보다 낮고, 22배 이상 느리며, 일관성 81%. 클로바(HCX-007·DASH-002)는 정확도·속도·일관성 모두 낮음

**한계**: LLM 하이브리드는 처음 보는 문서(synth_holdout)에서 측정하지 않았음. 규칙 단독이 holdout에서 0.972로 떨어지므로, LLM이 그쪽에서는 재현율을 더 올려 줄 가능성은 있음. 다만 규칙 + 토큰이 이미 0.988이고, 속도·외부 전송·일관성 문제는 그대로임

### 17-4. 참고: 고객 기준 채점 (baek 팀원 `tools/eval_customer.py`)
- 정답 중 **고객(roles의 C) 개인정보 458개만** 대상으로 하고, 직원 이름을 잡은 것은 틀린 것으로 치지 않는 기준
- test에서 규칙 단독도 고객 mask_rec·재현율 **1.000, 미끼 오탐 0** → 규칙이 놓친 것은 모두 직원 이름(메신저의 `은영이랑` 등)
- 보고서에서 "직원 이름까지 개인정보로 보는 데이터셋 기준"과 "고객 기준"을 함께 보여 줄 수 있음

### 17-5. 참고: 팀원 비교에서 발견된 LLM 특성
- GPT 계열이 `정 부장`에서 `정` 한 글자만 이름으로 답하면, 위치 찾기가 문서의 다른 `정`(`정지`, `정리`)까지 잡아 오탐이 생김 (gpt-4.1-mini 오탐 7건 중 다수)
- gpt-5.5는 메일 서명의 02 직통번호를 "회사 번호"로 보고 일부러 뺌 — 우리 LLM 실험(15장 이전 7-3)과 같은 현상
- 규칙과 LLM은 약점이 겹치지 않음: 규칙이 놓친 12개(이름만 부르기)를 LLM이 잡고, LLM이 놓친 번호를 규칙이 잡음 → 같은 원리로 규칙 + 토큰도 서로 메움

## 18. atonlee 줄바꿈 경계 버그 수정 (2026-10-23)

### 18-1. 문제
- 팀원 래퍼(`hf_ner.py`)는 문서 전체를 한 번에 처리해서, 개체가 **줄바꿈을 넘어 이어짐**: `김예준\n을`, `허 수아\n대상`, `달래\n박도윤`
- test 단독 경계 오류 60건 → atonlee 단독 strict F1이 실제보다 낮게 나옴 (0.933). 합집합은 규칙이 경계를 잡아 줘서 영향이 작았음

### 18-2. 처리 방식 비교 (`HFNerDetector(line_mode=…)`)
| 방식 | 단독 test strict F1 | 단독 test mask_rec | 합집합 test 정밀도 | 합집합 test mask_rec | 합집합 synth_dev mask_rec | 시간 |
|---|---|---|---|---|---|---|
| 수정 전 (줄 넘김 그대로) | 0.933 | 0.994 | 0.972 | 1.000 | 0.987 | 1배 |
| `split_all` 줄에서 잘라 모든 조각 유지 | 0.957 | 0.994 | 0.962 | 1.000 | 0.987 | 1배 |
| **`first` 첫 조각만 유지 (채택)** | 0.955 | 0.989 | **0.968** | **1.000** | **0.987** | **1배** |
| `per_line` 줄마다 따로 모델에 넣기 | 0.971 | 0.991 | 0.977 | 1.000 | 0.987 | 약 5배 (제공 데이터) |

- 모든 조각 유지는 뒷조각(`대상` 7건 등)이 이름 오탐이 되어 합집합 정밀도가 오히려 떨어짐
- 줄마다 따로 넣기가 가장 정확하지만 5배 느림 (줄이 많은 제공 문서 기준)
- **첫 조각만 유지 채택**: 속도는 그대로, 합집합 정밀도 개선. 뒷조각의 진짜 이름(`달래\n박도윤`의 `박도윤`)은 규칙이 잡음

### 18-3. 수정 후 최종 수치 (`results/system_comparison.csv`, `results/final_*`)

|---|---|---|---|---|

| 토큰 (atonlee) | 0.955 | 0.989 | 0.927 | 0.984 |
| **규칙 + 토큰** | **0.982** | **1.000** | **0.942** | **0.988** |

처리 시간 (이번 측정, 문서당 ms / 1만 건 분): 규칙 10.0 / 1.7분 · 토큰 102.0 / 17.0분 · 규칙+토큰 112.0 / 18.7분 (test), 일상 문서 4.3 / 78.9 / 83.2ms.
- 오전 측정(15-3)보다 약 2배 느림. 같은 날 두 번 재서 값이 일정했고, 코드가 아니라 PC 부하(브라우저·메신저 등) 차이로 판단 → **보고서에는 보수적으로 이번 값을 쓰고, PC 상태에 따라 2배까지 달라질 수 있다고 표기**
- 15-3의 수치는 수정 전 기준이므로 이 장의 수치가 최신

- 새로 생긴 형식 대부분은 **팀이 엣지 케이스·일상 문서로 미리 대비했던 것**(8·9·10·11장): 국제번호 `+82`, 은행별 계좌 자릿수, 붙여쓰기·공백 카드·주민번호, 지번·시도 줄임말 주소, 외자·복성 이름, 건물명 + 동·호수. 개선 전 점수가 유지된 이유(21장, mask_rec 0.993)로 볼 수 있음
- 미리 대비하지 못한 것: 이름 뒤 새 결합(`에게`, `인데요`, `의`), 한 글자 이름, 아파트 이름이 도로명 번지 바로 뒤에 쉼표 없이 붙는 주소, 계좌 3-2-6-1·2-6-6 같은 형식 → ⑦ 오류 분석에서 확인할 대상

## 24. ⑧ Holdout 개선 (v8, 2026-10-26)

> **순서**: 개선 전 평가 기록(21장) → 오류 분석(23장) → 개선(이 장) → holdout 재채점 → dev·test·엣지·일상 문서 재확인
> **주의**: 개선 후 holdout 점수는 holdout 오류를 보고 맞춘 결과라 **일반화 성능이 아님**. 일반화 확인은 dev·test·일상 문서 holdout 점수로 봄

### 24-1. 고친 것
| # | 대상 | 변경 (파일) | 해결한 holdout 오류 |
|---|---|---|---|
| 1 | 규칙 오탐 | 줄 맨 앞 `이름:` 규칙은 **문서 안에서 두 번 이상 말한 사람**이거나 서식 항목 접미사(`지·자·인·역·처·명·일·호`)로 끝나지 않을 때만 이름으로 봄. 명사 덩어리 규칙도 바로 뒤에 콜론이 오고 항목 접미사로 끝나면 제외 (`rule_based.py`) | `소명자:`, `위임인:`, `송금인:`, `배송지:` 오탐 34건 |
| 2 | 규칙 오탐 | 직함 `심사역·조사역·검사역·감사역·상담역` 추가, 부고 단어(`장인상` 등)는 이름 아님 | `심사역` 3건, `장인상` 2건 |
| 3 | 규칙 경계 | 사전에 없는 3글자 덩어리가 "이름 + 주격 조사 `이`"로 분석되면 조사를 뗌 | `안윤이`, `정별이` |
| 4 | 규칙 미탐 | 필드 추가(`수취인·송금인·위임인·소명자·피해자·검토자·신고인·청구인·확인자·승인자·심사역`), 사람만 올 수 있는 필드는 일반 단어와 같은 이름도 받음, **띄어 쓴 외자**(`전 찬`) | `신설`, `전 찬` |
| 5 | 규칙 형식 | 계좌 마지막 묶음 1자리(`056-75-340175-9`), 읍·면 바로 뒤 번지(`배방읍 252-4`), 주소 앞 우편번호(`(05299) …`) | 라벨 오류 3건, 경계 오류 5건 |
| 6 | 토큰 후처리 | 부고 단어·회사 이름 끝말(`보안`, `시스템즈` …)로 끝나는 이름 제거, 단어 중간을 자른 이름 제거(앞이 호칭·직급이면 예외: `회원박희정님`), `○○ 번호`(사건·접수·주문 등) 뒤·`내선` 뒤 번호와 연도-일련번호 제거, 이름 뒤 `드림`·주격 `이` 제거, 주소 앞 우편번호 포함 (`postprocess.py`) | `미르보안`, `조모상`, `미수(신)`, 사건번호 5건, 내선 2건, `시우 드림`, `오가은이` |

중간에 생긴 회귀와 수정
1. 콜론 앞 단어를 모두 서식 항목으로 봤더니 메신저에서 한 번만 말한 사람(`신승현:`)을 놓침 → 항목 접미사로 끝날 때만 거름 (합성어 판정은 `신승+현` 같은 이름도 걸려서 쓰지 않음)
2. 1글자 첫 단어를 필드 값으로 허용했더니 `고객: 김 과장`의 `김`을 잡음 → 1글자는 띄어 쓴 외자일 때만
3. 번호 문맥 정규식이 `주민등록번호`의 `등록번호`, `민원인: … (연락처 010…)`의 `민원`에 걸려 **토큰 단독의 주민번호·전화번호를 지움**(test mask_rec 0.989 → 0.939). 합집합은 규칙이 메워 드러나지 않았으나 구성 요소별 비교로 발견 → `○○ 번호` 꼴만 보도록 수정
4. 단어 중간 규칙이 `회원박희정님`(띄어쓰기 생략)을 지움 → 앞이 호칭·직급이면 예외

### 24-2. Holdout 개선 전 / 후 (규칙 + 토큰)
| | strict P | strict R | strict F1 | mask_rec | 미탐 | 오탐 | 경계 | 라벨 |
|---|---|---|---|---|---|---|---|---|
| 개선 전 (21장) | 0.912 | 0.978 | 0.944 | 0.993 | 3 | 65 | 14 | 3 |
| **개선 후** | **0.991** | **0.999** | **0.995** | **1.000** | **1** | **8** | 0 | 0 |

- 남은 미탐 1: 한 글자 이름 `린` / 남은 오탐 8: 형용사 `정다운`(공지 문서 반복) → 둘 다 일반화 위험이 커서 한계로 남김
- 어려운 사례(개선 후): 외자 이름 0.947 → **1.000**, 계좌 형식 0.957 → **1.000**, 주소 형식 0.951 → **1.000**, 이름만 0.985 → 0.993

### 24-3. 기존 데이터 재확인 — holdout에 맞춘 수정이 기존 성능을 떨어뜨렸나?
| 데이터 | strict F1 (전 → 후) | mask_rec (전 → 후) | strict P (전 → 후) |
|---|---|---|---|
| dev | 0.994 → 0.994 | 1.000 → 1.000 | 0.987 → 0.987 |
| test | 0.982 → **0.986** | 1.000 → 1.000 | 0.968 → **0.976** |
| 엣지 케이스 | 0.979 → **0.983** | 1.000 → 1.000 | 0.959 → **0.967** |
| 일상 문서 개선용 | 0.959 → **0.969** | 0.987 → 0.987 | 0.934 → **0.952** |
| 일상 문서 holdout | 0.942 → **0.956** | 0.988 → 0.988 | 0.909 → **0.934** |

- **모든 데이터에서 떨어진 지표 없음**. 정답과 정확히 일치하던 개체를 새로 놓친 경우 0건(전후 비교로 확인)
- 특히 **오류를 한 번도 보지 않은 일상 문서 holdout에서도 정밀도가 0.909 → 0.934로 올라** 이번 수정(서식 항목·회사·사건번호 오탐 제거)이 holdout에만 맞춘 것이 아니라는 근거

## 26. 2차 평가 세트 synth_fresh 생성·검수·첫 채점 (2026-10-26)

### 26-1. 생성 (`tools/generate_synthetic.py --set fresh`, gpt-4.1, temperature 0.9)

## 30. 탐지기 v10: '이'로 끝나는 이름 처리 (2026-10-26)

### 30-1. 문제 (사용자 질문: "백송이처럼 '이'로 끝나는 이름은?")
- v8에서 `안윤이 조건 안내`를 고치려고 넣은 두 규칙(규칙: 사전에 없는 3글자가 "이름 + 주격 조사 이"로 분석되면 `이`를 뗌 / 토큰 후처리: 3글자 이상 이름이 `이`로 끝나고 뒤가 공백·문장부호면 `이`를 뗌)이 `백송이`도 `백송`으로 자름. Kiwi도 `백송이`를 `백송 + 이(JKS)`로 분석
- v9에서 확인: `백송이 대리가`, `고객 백송이 님이`, `백송이 드림`, `심사역 백송이 조건 안내` → `백송` / `백송이가`, `백송이님`, `성명: 백송이` → `백송이`. 같은 사람이 문서 안에서 다른 경계로 잡혀 실전 2에서 다른 가명 토큰이 될 수 있음

### 30-2. 고친 것 (`postprocess.resolve_name_i`, 규칙 끝과 토큰 후처리 끝에서 공통 사용)
이름 끝 `이`를 이름에 넣을지(긴 이름 `백송이`) 뺄지(짧은 이름 `안윤`) 두 단서로 정함
1. **같은 문서 안 다른 표기**: 긴 이름 뒤에 직함·호칭이 온 곳(`백송이님`, `백송이 대리`, `백송이 드림`)이 있으면 긴 이름, 짧은 이름이 `이` 없이 쓰인 곳(`안윤님`, `안윤 대리`, `안윤의`, `안윤은`, `안윤에게`)이 있으면 짧은 이름. 한쪽만 있을 때 그쪽으로. `백송이가`·`백송이는`은 받침 있는 이름 + 접사 `이`(`은영이가`)로도 읽혀 단서로 쓰지 않음
2. **이 자리 바로 뒤**: 문서 단서가 없으면, 바로 뒤가 직함·호칭이면 긴 이름(주격 조사 `이` 뒤에는 직함·호칭이 바로 올 수 없음)
3. 둘 다 없으면 탐지기 경계 그대로(`심사역 백송이 조건 안내`는 구분 불가 → 한계)
- 안전장치: `이`까지 붙인 이름은 3글자까지, 4글자는 복성일 때만(`김미영이` → `김미영`). 띄어 쓴 성 `브라이언 이`는 건드리지 않음. `고객`은 `김미영이 고객 상담을`처럼 일반 명사로 와서 `고객님`만 단서로 씀

중간 회귀와 수정 (모든 세트 재채점으로 발견)
1. 처음에 `고객`을 호칭 단서로 넣었더니 멘토 holdout `김미영이 고객 …`(주격 조사)이 `김미영이`로 늘어 정확 일치 27건 손실 → `고객님`만, 4글자 제한 추가
2. 줄 끝 `이`를 떼지 않게 했더니 fresh `최하윤이⏎주소…`(줄에서 문장이 끊김) 17건 손실 → 되돌림(`성명: 백송이`는 규칙 필드 규칙이 잡아 합집합에서 유지)
3. 띄어 쓴 성 `브라이언 이`가 `브라이언`으로 잘림 → 예외 추가
