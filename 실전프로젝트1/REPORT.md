## 1. 데이터 관찰 요약 (상세: `results/eda/report.md`)

- 개체의 62~67%가 `person`. 표기는 전체 이름(full) 88%, 띄어 쓴 이름(spaced) 7%, 이름만(given) 6%.
- 이름 뒤 조사·호칭 부착이 많음: `님께서`, `님은`, `입니다`, `이랑`, `아` 등. 표기가 2가지 이상인 인물이 test 72명 중 41명 → 가명처리 토큰 일관성(실전 2)에 직접 영향.
- 전화번호 형식 8종(하이픈·점·공백·붙여쓰기, 02 지역번호). 주민·계좌·카드는 형식이 하나뿐.
- 오탐 미끼: 대표번호 `1599-0000`, 날짜·민원번호, 상품명(`한결 플러스 카드`), **라벨 없는 성+직함**(`허 부장`, `김 대리`; test 40건).
- **test 템플릿 23종이 전부 dev에 있음** → test는 holdout보다 낙관적일 수밖에 없음.

**팀 라벨 기준** (데이터셋 정답 기준을 따름, `detectors/base.py`)
- 잡는다: 전체 이름·이름만·띄어 쓴 이름, 고객·직원 전화(직통 포함), 이메일, 주소, 주민·계좌·카드번호
- 범위에서 뺀다: 조사·호칭 (`윤선영은` → `윤선영`)
- 잡지 않는다: `김 과장`처럼 성+직함만 있는 표현, 회사 대표번호·내선, 회사·부서·상품명
- `김 과장`을 잡지 않는 이유: 성 한 글자와 직함만으로는 개인을 특정하기 어렵고, 잡으면 실전 2에서 서로 다른 '김 과장'들이 한 토큰으로 합쳐짐. 다만 같은 문서에 이름이 함께 나오면 재식별 단서가 될 수 있어, 종합 단계에서 출력 재검사 대상으로 다시 검토할 항목으로 남김.

방식별 약점 정리
- **규칙**: 데이터에 있는 문구에서는 거의 완벽하지만, 성씨 목록에 없는 성(`예`)·목록에 없는 호칭(`손님`)·새 조사 결합에서 놓침 → 미탐형 약점, 새 문서에서 무너질 위험.
- **토큰 분류**: 정형 번호는 다 잡지만 문맥상 개인정보가 아닌 번호(대표번호)를 구분 못 함 → 오탐형 약점. 정답과 경계 기준이 달라 strict가 낮음.
- **LLM**: 오탐과 경계 오류는 거의 없지만, 지시를 따라도 반복적으로 빠뜨리는 유형이 있음 → 미탐형 약점. "직원 직통번호도 개인정보인가"처럼 기준이 애매한 곳에서 자기 판단을 씀.

### 형태소 분석기(Kiwi)가 어려운 표현을 쪼개는 방식

| 입력 | Kiwi 결과 | 시사점 |
|---|---|---|
| `윤선영은` | 윤/NNP + 선영/NNG + 은/JX | 조사는 분리되지만 이름이 성(NNP)+일반명사로 쪼개짐 → NNP 태그만으로는 이름을 못 묶음 |
| `윤 선영` | 윤/NNP + 선영/NNG | 띄어 쓴 이름은 '성 한 글자 어절 + 다음 어절' 규칙으로 따로 처리해야 함 |
| `김은영 상담원` | 김/NNP + **은/JX** + 영/NNG + 상담원/NNG | 이름 가운데 글자 `은`을 조사로 오분석 → 형태소 결과를 그대로 쓰면 `김`만 남음. 규칙은 어절 단위 후보 + 호칭 근거로 판단하고 Kiwi는 보조로만 씀 |
| `허 부장님이` | 허/NNP + 부장/NNG + 님/XSN + 이/JKS | 성+직함 구조가 잘 보임 → 팀 기준대로 제외 가능 |
| `한결 플러스 카드` | 한결/MAG + 플러스/NNG + 카드/NNG | 고유명사로 보지 않아 이름 오탐 위험이 낮음 |

### 라벨별로 방식을 나눠 쓰면?

정형 라벨(전화·이메일·주민·계좌·카드·주소)은 규칙이 재현율·정밀도 모두 1.000이고 16ms로 가장 빠름. 모델·LLM의 정형 라벨 결과는 오히려 오탐(대표번호)이나 미탐(직통번호)만 더함. 반면 이름은 문맥 의존이라 규칙의 일반화가 불안함. 그래서 **정형 라벨 = 규칙, 이름 = 규칙 ∪ 모델**로 나눈 하이브리드가 test에서 규칙 수준 정확도를 유지하면서, 새 문장에서 규칙이 놓친 이름을 모델이 보완함(6장).

## 5. LLM 실험 상세

### 프롬프트 개선 과정 (dev 기준, 개선은 dev에서만)

| 버전 | 변경 | dev strict R | person R |
|---|---|---|---|
| v1 | 7종 라벨·조사 제외·성+직함 제외 규칙 | 0.896 | 0.844 |
| v2 | "직원·상담원·참석자 이름도 person", "이름+직함이면 이름만", 이름만 부르기 예시 추가 | 0.929 | 0.894 |
| v3 (최종) | 후처리: 같은 문서 안 띄어쓰기 변형(`노 성호` ↔ `노성호`) 전파, 한 글자·성+직함 문자열 제거 | 0.967 | 0.953 |

- v1에서 `성+직함 제외` 규칙 때문에 LLM이 `허수아 부장`, `박 예린 팀장`처럼 **이름이 있는 경우까지** 통째로 버림 → 지시문 한 줄이 재현율을 크게 바꿈.
- 프롬프트 예시에는 데이터셋에 없는 가상 이름(홍길동, 정 다온 등)만 씀 (정답 엿보기 방지).
- 버그 수정: LLM이 `정 부장`에서 `정` 한 글자를 돌려주면 원문 전체에서 `정`을 찾아 `정지`·`일정`까지 오탐 → 한 글자 이름 제거로 해결 (test 오탐 14 → 2).

### LLM으로 같은 문서를 3번 돌리면 같은가?

temperature 0이어도 **같지 않음**. test 200건 중 95.5%만 3회 결과가 완전히 같고(평균 Jaccard 0.995), 1회차와 2회차의 탐지 수가 1,124 / 1,120 / 1,122로 다름. 규칙·토큰 분류 모델은 100% 동일. 가명처리에서는 같은 문서를 다시 적재할 때 토큰 목록이 바뀔 수 있다는 뜻이라, 감사·재현이 필요한 운영 파이프라인의 주 탐지기로 쓰기 어려움.

### 실제 고객 문서를 클라우드 LLM에 보내도 되는가?

안 됨. 개인정보를 찾으려고 원문을 외부로 보내는 순간 이미 유출(제3자 제공·국외 이전)이 발생하는 모순. 이번 실험은 가상 데이터라서만 허용됨. LLM 탐지를 운영에 쓰려면:
1. **사내(온프레미스) LLM**: 로컬 서버를 OpenAI 호환 방식으로 띄우고 `LLM_BASE_URL`만 바꿔 같은 코드 사용 (CPU 서버 가정이면 속도 문제가 더 커짐).
2. **2단계 구조**: 규칙+모델로 먼저 가린 텍스트만 LLM에 보내 "남은 개인정보가 있는지" 재검사 → 외부로 나가는 원문 노출을 줄임 (종합 단계의 출력 재검사와 같은 구조).
3. **오프라인 보조 용도**: 운영 탐지가 아니라, 가상 데이터로 규칙·모델의 미탐 후보를 찾는 검수 도구로만 사용.

## 6. 처음 보는 문서에서도 통할까? (holdout 대용 점검)

holdout을 받지 못해, 데이터셋에 없는 문장 구조로 직접 쓴 예문 10개(개인정보 12개, 미끼 1문장)로 점검함. 정량 평가가 아니라 경향 확인용.

| 시스템 | 재현 | 오탐 | 놓친 것 / 잘못 잡은 것 |
|---|---|---|---|
| rules | **9/12** | 0 | `배다온 손님`(호칭 목록에 '손님' 없음), `송하람한테`, `예서윤`(성씨 목록에 '예' 없음) |
| veil | 11/12 | 2 | `배다온`, 한글로 쓴 번호 `공일공-일이삼사-…`를 전화로, `김 과장`의 `김` |
| seongyeon | 11/12 | 1 | `배다온`, `김` |
| llm | **12/12** | 0 | — |
| hybrid_seong | 11/12 | 0 | `배다온` |

- test에서 1위였던 규칙이 여기서는 꼴찌. 규칙은 dev 문서의 호칭·조사·성씨 범위에 기대고 있어 **test와 holdout의 순위가 뒤바뀔 가능성이 가장 큰 방식**. 점수가 가장 많이 떨어질 후보도 규칙.
- 하이브리드는 규칙이 놓친 3건 중 2건을 모델이 보완 → 규칙 단독보다 하이브리드를 고른 핵심 근거.
- holdout을 받으면 `python run_detect.py --detector hybrid_seongyeon --data data/holdout.jsonl`로 같은 방식으로 최종 평가 예정.

### 이름 사전에 personas.json을 쓰지 않은 이유

`personas.json`은 데이터셋을 만든 가상 인물 목록이라, 이를 사전으로 쓰면 탐지가 아니라 **정답 조회**가 됨. dev·test·holdout 인물이 겹치면 점수가 부풀고, 실제 운영에서는 존재할 수 없는 정보(앞으로 나올 모든 고객 이름)를 가정하게 됨. 그래서 규칙은 **일반 성씨 목록(단성 82개 + 복성 8개)과 호칭·조사 규칙**만 씀. 그 대가가 6장의 `예서윤` 미탐처럼 드문 성씨를 놓치는 것이고, 이것이 모델과 합치는 이유이기도 함.

## 7. 탐지기 선정 근거

**선정: `hybrid_seong` (정형 라벨 = 규칙, 이름 = 규칙 ∪ seongyeon)**

1. **재현율·mask_rec 최상위**: test 재현율 0.997, mask_rec 1.000, 미탐 0건. 경계 오류 4건은 이름 뒤 호격조사까지 더 가린 것이라 개인정보 노출은 없음(단, 실전 2 정규화에서 `은영이` → `은영`으로 조사를 떼야 토큰이 같아짐).
2. **오탐 거의 없음**: 미끼 문서 오탐 0, 전체 오탐 2건(상품명 `하린 포인트 카드`의 `하린`) → 실전 2 검색에서 엉뚱한 토큰이 거의 생기지 않음.
3. **CPU에서 충분히 빠름**: 문서당 158ms, 1만 건 약 26분. GPU 불필요.
4. **결과 일관성 100%**: 같은 문서 → 같은 탐지 → 같은 토큰. 가명처리·재적재에 필수.
5. **원문이 외부로 나가지 않음**: 실전 2·종합의 "마스킹 텍스트만 외부 전송" 원칙과 맞음.
6. **일반화 보완**: 규칙이 새 문장에서 놓친 이름을 모델이 보완(6장).

veil과의 비교: hybrid_veil도 재현율은 같지만 veil이 대표번호·미끼 단어를 이름으로 잡아 오탐 15건. seongyeon은 경계는 거칠지만 이름 재현율이 1.000이고 하이브리드에서는 규칙 경계를 우선해 단점이 가려짐. 단, seongyeon은 **CC-BY-SA-4.0**이라 사내 배포 형태에 따라 라이선스 검토가 필요하며, 문제가 되면 Apache-2.0인 veil(hybrid_veil, F1 0.990)로 바꿀 수 있음.

**LLM의 역할**: 운영 탐지기가 아니라 (a) 사내 LLM이 있을 때 종합 단계의 **출력 재검사**, (b) 개발 단계에서 규칙의 미탐 후보를 찾는 **검수 도구**로 활용.

## 8. 실전 2로 넘길 것

- 같은 인물 표기 변형(`윤 선영`/`윤선영`) → 정규화(공백 제거) 후 HMAC. 이번 LLM 후처리의 띄어쓰기 변형 전파와 같은 원리.
- 동명이인(`김민준` 2명, `정하은` 2명 등): 이름만으로 토큰을 만들면 합쳐짐 → 종합에서 문맥(직원/고객, 소속) 반영 필요.
- `김 과장` 같은 미라벨 성+직함은 가리지 않으므로 출력 재검사 대상에 포함 여부 결정 필요.
