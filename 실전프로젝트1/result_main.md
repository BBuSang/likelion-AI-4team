방식별 약점
- **규칙**: 데이터에 있는 문구에서는 거의 완벽. 성씨 목록에 없는 성(`예`), 목록에 없는 호칭(`손님`), 새 조사 결합에서 놓침 → 새 문서에서 무너질 위험.
- **토큰 분류**: 정형 번호는 다 잡지만 문맥상 개인정보가 아닌 번호(대표번호)를 구분 못 함 → 오탐형 약점. 정답과 경계 기준이 달라 strict가 낮음.
- **LLM**: 오탐·경계 오류는 거의 없지만 지시를 줘도 반복적으로 빠뜨리는 유형이 있음 → 미탐형 약점. 기준이 애매한 곳(직원 직통번호)에서 자기 판단을 씀.

### 형태소 분석기(Kiwi)가 어려운 표현을 쪼개는 방식

| 입력 | Kiwi 결과 | 시사점 |
|---|---|---|
| `윤선영은` | 윤/NNP + 선영/NNG + 은/JX | 조사는 분리되지만 이름이 성+일반명사로 쪼개짐 → NNP 태그만으로는 이름을 못 묶음 |
| `윤 선영` | 윤/NNP + 선영/NNG | 띄어 쓴 이름은 '성 한 글자 어절 + 다음 어절' 규칙으로 따로 처리 |
| `김은영 상담원` | 김/NNP + **은/JX** + 영/NNG + 상담원/NNG | 이름 가운데 `은`을 조사로 오분석 → 규칙은 어절 단위 후보 + 호칭 근거로 판단하고 Kiwi는 보조로만 씀 |
| `허 부장님이` | 허/NNP + 부장/NNG + 님/XSN + 이/JKS | 성+직함 구조가 잘 보임 |
| `한결 플러스 카드` | 한결/MAG + 플러스/NNG + 카드/NNG | 고유명사로 보지 않아 이름 오탐 위험이 낮음 |

### 라벨별로 방식을 나눠 쓰면?

정형 라벨(전화·이메일·주민·계좌·카드·주소)은 규칙이 재현율·정밀도 모두 1.000이고 가장 빠름. 모델·LLM의 정형 라벨 결과는 오탐(대표번호)이나 미탐(직통번호)만 더함. 이름은 문맥 의존이라 규칙의 일반화가 불안함 → **정형 라벨 = 규칙, 이름 = 규칙 ∪ 모델**로 나눈 하이브리드를 선택.

모든 탐지기가 성+직함을 일부러 빼도록 만들어져 있어 40건을 그대로 놓침 → 재현율이 일제히 약 3.3%p 하락.

### 탐지기에 반영한 뒤 (test, 정답 1,205개)

| 시스템 | strict P | strict R | strict F1 | partial R | mask_rec | 미끼 문서 오탐 |
|---|---|---|---|---|---|---|
| rules | 0.997 | 0.996 | 0.996 | 0.999 | 1.000 | 0 |
| veil | 0.938 | 0.960 | 0.949 | 0.980 | 0.991 | 33 |
| seongyeon | 0.865 | 0.911 | 0.888 | 1.000 | 0.914 | 2 |
| llm (프롬프트만 변경) | 0.957 | 0.939 | 0.948 | 0.980 | 0.981 | 0 |
| llm (프롬프트 + 규칙) | 0.953 | 0.939 | 0.946 | 0.983 | 0.984 | 0 |
| hybrid_veil | 0.984 | 0.997 | 0.991 | 1.000 | 1.000 | 8 |
| **hybrid_seong** | **0.995** | **0.997** | **0.996** | **1.000** | **1.000** | 0 |
| hybrid_union | 0.984 | 0.997 | 0.991 | 1.000 | 1.000 | 8 |
| hybrid_vote | 0.995 | 0.997 | 0.996 | 1.000 | 1.000 | 0 |

- **규칙·하이브리드**: 성+직함 40건을 모두 잡고 오탐은 늘지 않음 → 기준이 바뀌어도 선정 결과는 그대로. 단, 정답과 탐지 규칙이 비슷한 패턴(성 + 직함)이라 이 수치는 낙관적.
- **LLM은 경계 기준이 흔들림**
  - 프롬프트만 바꿔도 성+직함 40건 중 38건을 잡음(놓친 것: `전 팀장`, `이 팀장`).
  - 대신 `허수아` → `허수아 부장`처럼 이름이 다 있는 경우에도 직함을 붙여, 경계 오류가 2건 → 54건. strict 정밀도가 0.996 → 0.953으로 떨어진 이유.
  - 그 덕분에 예전에 계속 놓치던 `허수아`가 잡혀 partial 재현율은 0.963 → 0.983으로 오름.
  - 3회 실행 일관성은 95.5% → 92.0%로 낮아짐. 지시문 한 줄이 출력 범위를 넓게 바꾼다는 점이 LLM 탐지의 운영 위험.
- **선정 영향**: 성+직함을 포함하면 실전 2에서 서로 다른 `김 과장`들이 한 토큰으로 합쳐질 수 있음 → 토큰을 만들 때 문서·소속 정보를 함께 쓸지 결정 필요.

## 6. LLM 실험 상세

### 프롬프트 개선 과정 (dev에서만 조정)

| 버전 | 변경 | dev strict R | person R |
|---|---|---|---|
| v1 | 7종 라벨·조사 제외·성+직함 제외 규칙 | 0.896 | 0.844 |
| v2 | "직원·상담원·참석자 이름도 person", "이름+직함이면 이름만", 이름만 부르기 예시 추가 | 0.929 | 0.894 |
| v3 (최종) | 후처리: 같은 문서 안 띄어쓰기 변형(`노 성호` ↔ `노성호`) 전파, 한 글자·성+직함 문자열 제거 | 0.967 | 0.953 |

- v1에서 `성+직함 제외` 규칙 때문에 LLM이 `허수아 부장`, `박 예린 팀장`처럼 이름이 있는 경우까지 통째로 버림.
- 프롬프트 예시에는 데이터셋에 없는 가상 이름(홍길동, 정 다온 등)만 씀 (정답 엿보기 방지).
- 버그 수정: LLM이 `정 부장`에서 `정` 한 글자를 돌려주면 원문 전체의 `정`(`정지`, `일정`)까지 잡힘 → 한 글자 이름 제거로 test 오탐 14 → 2건.

### 같은 문서를 3번 돌리면 같은가?

temperature 0이어도 **같지 않음**. test 200건 중 95.5%만 3회 결과가 완전히 같고(평균 Jaccard 0.995), 회차별 탐지 수가 1,124 / 1,120 / 1,122로 다름. 규칙·토큰 분류 모델은 100% 동일. 같은 문서를 다시 적재할 때 토큰 목록이 바뀔 수 있다는 뜻이라, 재현성이 필요한 가명처리의 주 탐지기로는 부적합.

### 실제 고객 문서를 클라우드 LLM에 보내도 되는가?

안 됨. 개인정보를 찾으려고 원문을 외부로 보내는 순간 이미 유출(제3자 제공·국외 이전)이 됨. 이번 실험은 가상 데이터라서만 허용됨. LLM을 운영에 쓰려면:
1. **사내(온프레미스) LLM**: 로컬 서버를 OpenAI 호환 방식으로 띄우고 `LLM_BASE_URL`만 바꿔 같은 코드 사용 (CPU 서버라면 속도 문제가 더 커짐).
2. **2단계 구조**: 규칙+모델로 먼저 가린 텍스트만 LLM에 보내 남은 개인정보를 재검사 (종합 단계의 출력 재검사와 같은 구조).
3. **오프라인 검수 도구**: 운영 탐지가 아니라, 규칙·모델의 미탐 후보를 찾는 개발용으로만 사용.

## 7. 처음 보는 문서에서도 통할까? (holdout 대용 점검)

holdout이 없어, 데이터셋에 없는 문장 구조로 직접 쓴 예문 10개(개인정보 12개, 미끼 1문장)로 점검함 (`probe_unseen.py`). 정량 평가가 아니라 경향 확인용.

| 시스템 | 재현 | 오탐 | 놓친 것 / 잘못 잡은 것 |
|---|---|---|---|
| rules | **9/12** | 0 | `배다온 손님`(호칭 목록에 '손님' 없음), `송하람한테`, `예서윤`(성씨 목록에 '예' 없음) |
| veil | 11/12 | 2 | `배다온`, 한글로 쓴 번호 `공일공-일이삼사-…`를 전화로, `김 과장`의 `김` |
| seongyeon | 11/12 | 1 | `배다온`, `김` |
| llm | **12/12** | 0 | — |
| hybrid_seong | 11/12 | 0 | `배다온` |

- test 1위였던 규칙이 여기서는 꼴찌 → **test와 holdout의 순위가 뒤바뀔 가능성이 가장 큰 방식, 점수가 가장 많이 떨어질 후보**.
- 하이브리드는 규칙이 놓친 3건 중 2건을 모델이 보완 → 규칙 단독 대신 하이브리드를 고른 핵심 근거.
- holdout을 받으면: `python run_detect.py --detector hybrid_seongyeon --data data/holdout.jsonl`

### 이름 사전에 personas.json을 쓰지 않은 이유

`personas.json`은 데이터셋을 만든 가상 인물 목록이라, 사전으로 쓰면 탐지가 아니라 **정답 조회**가 됨. 인물이 겹치는 dev·test·holdout 점수가 부풀고, 운영에서는 존재할 수 없는 정보(앞으로 올 모든 고객 이름)를 가정하게 됨. 그래서 규칙은 **일반 성씨 목록(단성 82개 + 복성 8개)과 호칭·조사 규칙**만 씀. 그 대가가 `예서윤`처럼 드문 성씨를 놓치는 것이고, 이것이 모델과 합치는 이유이기도 함.

## 8. 탐지기 선정 근거

**선정: `hybrid_seong`**

1. **재현율·mask_rec 최상위**: test 재현율 0.997, mask_rec 1.000, 미탐 0건. 경계 오류 4건은 이름 뒤 호격조사까지 더 가린 것이라 노출 없음 (실전 2 정규화에서 `은영이` → `은영`으로 조사를 떼야 토큰이 같아짐).
2. **오탐 거의 없음**: 미끼 문서 오탐 0, 전체 오탐 2건(상품명 `하린 포인트 카드`의 `하린`).
3. **CPU에서 충분히 빠름**: 문서당 약 160ms, 1만 건 약 26분. GPU 불필요.
4. **결과 일관성 100%**: 같은 문서 → 같은 탐지 → 같은 토큰. 가명처리·재적재에 필수.
5. **원문이 외부로 나가지 않음**: 실전 2·종합의 "마스킹 텍스트만 외부 전송" 원칙과 맞음.
6. **기준 변경에 강함**: 성+직함 포함 기준에서도 F1 0.996 그대로.
7. **일반화 보완**: 새 문장에서 규칙이 놓친 이름을 모델이 보완.

다른 후보와의 비교
- **hybrid_vote**: 점수는 같지만 모델 2개를 돌려 시간이 2~3배 → 지금 데이터에서는 이득 없음. 규칙이 무너지는 holdout에서 다시 확인할 가치는 있음.
- **hybrid_veil / hybrid_union**: veil이 대표번호·미끼 단어를 이름으로 잡아 오탐 15건.
- **라이선스**: seongyeon은 CC-BY-SA-4.0이라 배포 형태에 따라 검토 필요. 문제가 되면 Apache-2.0인 veil 조합(hybrid_veil, F1 0.990)으로 교체 가능.
- **LLM의 역할**: 운영 탐지기가 아니라 (a) 사내 LLM이 있을 때 종합 단계의 출력 재검사, (b) 개발 단계에서 규칙의 미탐 후보를 찾는 검수 도구.

## 9. 실전 2로 넘길 것

- 같은 인물 표기 변형(`윤 선영`/`윤선영`, `은영이`/`은영`) → 공백·조사 정규화 후 HMAC.
- 동명이인(`김민준`, `정하은`, `박도윤`, `이서연` 각 2명): 이름만으로 토큰을 만들면 합쳐짐 → 종합에서 문맥(직원/고객, 소속) 반영 필요.
- 성+직함을 포함할지 최종 결정. 포함하면 서로 다른 `김 과장`이 한 토큰으로 합쳐지는 문제를 함께 해결해야 함.

## 12. 규칙 개선 — 조사 받침 규칙과 호칭 추가

하이브리드에 남아 있던 오류를 줄이기 위해 규칙 기반(`detectors/rules.py`)의 이름 규칙 두 가지를 고치고, 규칙 단독과 토큰 하이브리드 7종을 다시 돌림. **1~11장의 수치는 수정 전 규칙 기준**이고, 이 장의 결과는 `preds_josa/`, `results/compare_josa_*`에 따로 저장함. (`hybrid_llm`은 API를 다시 호출해야 해서 이번에는 제외.)

### 수정 내용

**① 조사 받침 규칙 — 경계 오류 해결**

- 문제: `은`, `서`, `소`, `성`이 성씨 목록에 있어서, `은영이랑`을 '은(성) + 영이(이름) + 랑(조사)'으로 읽어 3글자 이름 `은영이`를 잡음. test의 경계 오류 4건(`은영이`, `서연이`, `소율아`, `성호야`)이 모두 이 경우.
- 수정: 어절 앞 3글자가 '이름 2글자 + 조사'로 읽히면 3글자 이름으로 보지 않음. 한국어 조사가 받침 유무에 따라 `이랑/랑`, `아/야`로 갈리는 원리를 그대로 씀.

| 경우 | 판단 | 예 |
|---|---|---|
| 둘째 글자에 받침 있음 + `이`·`아` | 이름 2글자 + 조사 | `은영`+`이랑`, `서연`+`이랑`, `소율`+`아` |
| 둘째 글자에 받침 없음 + `야` | 이름 2글자 + 조사 | `성호`+`야` |
| 둘째 글자에 받침 없음 + `아` | 3글자 이름 그대로 | `김서아`, `이지아` |

**② 호칭 목록 추가 — 미탐 해결**

- 문제: `배다온 손님`처럼 이름 뒤에 오는 말이 호칭 목록에 없으면 이름의 근거로 인정되지 않음.
- 수정: 이름 자체는 아니지만 **이름 뒤에 붙어 사람임을 알려주는 말** 8개를 호칭 목록(이름 판단 근거)에 추가: `손님`, `가입자`, `신청인`, `민원인`, `예금주`, `명의자`, `보호자`, `환자`.
- 이 말들은 이름으로 잡지 않음. 규칙은 앞에 '성 + 이름 2글자'가 있어야 후보를 만들므로, `민원인에게 회신`·`손님 응대 매뉴얼`처럼 혼자 쓰인 경우는 그대로 잡지 않음(예문으로 확인).

**예문 확인 (15개)**: 수정 전 8/15 → 수정 후 14/15. 남은 1건(`윤선영은 다시 연락`처럼 근거 단서 없이 이름만 있는 문장)은 수정 전에도 못 잡던 것. 실제 문서에서는 같은 이름이 근거와 함께 다른 곳에 나오면 문서 안 전파로 잡힘.

| hybrid_bccard | 0.991 → 0.991 | 0.986 → 0.989 | 9 → 5 |

- dev는 수정 전에도 경계 오류가 0건이라 변화 없음 (dev로 다듬은 규칙이 dev의 조사 결합은 이미 맞게 처리하고 있었고, 틀린 4건은 모두 test에서만 나옴).
- 성+직함 기준에서 hybrid_e5·hybrid_bccard에 남은 경계 오류는 모델이 `김 대리가`처럼 조사까지 붙여 잡은 경우(e5 9건, bccard 5건). 이번 규칙 수정 대상이 아님.

### 처음 보는 문장 점검 (`probe_unseen.py`)

세트 1은 이번 수정에 참고한 예문(`배다온 손님`)이 들어 있어 **더 이상 '처음 보는 문장'이 아님**. 그래서 규칙을 고친 뒤 결과를 보기 전에 새 예문 13개(개인정보 14개, 미끼 1문장)로 **세트 2**를 만들어 함께 점검함. 세트 2에는 받침 조사(`채린이가`, `지수야`), 새 호칭(`가입자분`), 드문 성씨(`국하늘`, `황보진숙`), 이름 나열(`금다인, 육서진, 탁민호`), 공백 구분 카드번호, 4덩어리 계좌번호 등을 넣음.

| 시스템 | 세트 1 (전 → 후) | 세트 2 (전 → 후) |
|---|---|---|
| rules | 9/12 → 10/12 | 11/14 → 12/14 |
| hybrid_veil | 11/12 → **12/12** | 14/14 |
| hybrid_seong | 11/12 → **12/12** | 14/14 |
| hybrid_kpf | 11/12 → **12/12** | 14/14 |
| hybrid_atonlee | 12/12 → 12/12 | 14/14 (`지수야`로 한 글자 길게 잡음) |
| hybrid_dlp | 11/12 → **12/12** | 14/14 |
| hybrid_e5 | 11/12 → **12/12** | 14/14 |
| hybrid_bccard | 11/12 → 11/12 | 13/14 |

- 세트 2의 하이브리드 '전' 값은 수정 전 규칙으로 돌리지 않아 비워 둠(규칙 단독만 비교).
- 수정 후 규칙이 세트 2에서 새로 잡은 것: `류하진 가입자분`.
- 규칙이 여전히 못 잡는 것 (하이브리드에서는 대부분 모델이 보완):
  - `지수야`: Kiwi가 `지수`를 일반명사(지수·지표)로 분석해 이름 근거가 약하다고 판단. hybrid_bccard도 놓침.
  - `황보진숙이시고`: `이시고`가 조사 목록에 없어 이름과 분리되지 않음.
  - (세트 1) `송하람한테`(근거 단서 없음), `예서윤`(성씨 목록에 `예` 없음).

### 정리

- 받침 조사 규칙은 문서 문구가 아니라 한국어 조사 규칙에 기댄 일반 규칙이라, 처음 보는 문장(세트 2)에서도 오탐 없이 동작함.
- **선정 결과는 그대로 `hybrid_seong`**(test F1 0.999, 158ms 수준). 다만 hybrid_dlp가 test 오류 0건으로 정확도 1위를 굳혀, 라이선스(Apache-2.0)까지 고려하면 대체 후보로서 근거가 더 강해짐.
- 남은 과제: 근거 단서 없는 이름(`송하람한테`), 목록에 없는 성씨(`예`), `-이시고` 같은 서술격 조사 결합. 셋 다 규칙만으로는 한계가 있어 모델 보완과 출력 재검사가 필요함.
