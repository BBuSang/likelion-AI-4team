## 2. 최종 구성

```
질문
 → ① KURE-v1 임베딩 (CPU, 약 0.2초)
 → ② pgvector 조각 50개 → 조문 단위로 합침 (조문 점수 = 조각 최고점)
 → ③ 후보 = 1~10위 + 1~5위에 위임·준용으로 연결된 조문 중 10위 밖 (`article_links`)
 → ④ 조문 글: 여러 조각 조문은 2,000자 이하면 전체, 넘으면 검색에 걸린 조각 전부
 → (1위 점수 < 0.5338 이면 LLM 없이 '관련 조문을 찾지 못했습니다')
 → ⑤ LLM 한 번 (추론 low): {"근거": [후보 번호 최대 3], "답변": "2~4문장"}
 → 답변 + 근거 조문(출처·시행일자·본문·국가법령정보센터 링크)
```

함수 하나: `retriever/answer.py`의 `answer(question)` — 평가·데모·팀 서비스가 같이 쓴다.

## 9. 과적합을 막으려고 한 것

- 규칙은 **기획안에 먼저** 적고, 법령·조문·질문 이름을 쓰지 않는 일반 구조 규칙만 씀 (조문 제목·문장 모양·조각 수·글자 수·위임 문장)
- 결과를 본 세트와 확인하는 세트를 나눔: 규칙은 dev에서 만들고, 채택 전에 그 규칙에 안 쓴 dev로 다시 확인 (정의 청크 → dev4, 합친 후보·조문 글 → dev7·8, 기준점수 → dev6~10·na_test, 지시문 → 새 답변불가 20)
- test는 세트마다 한 번만, 결과를 보고 고치지 않음 (잠금 코드)
- 기준값이 문항에 묶였는지 확인: 조문 글 기준 2,000자를 1,500·3,000자로 바꿔도 dev 정답 조문 104개가 모두 같은 결과
- 같은 설정 재실행 흔들림을 따로 재서(107문항에서 1위 정답 3문항이 바뀜) 1~2문항 차이를 효과로 단정하지 않음

| 숫자 계산 | 추론 low에서 '과반수' 같은 계산이 가끔 틀림 (같은 입력 10번 중 1번) | 계산형 질문 따로 평가 |
| 참고 조문 근거 | 범위 밖 질문 일부에서 '없다'고 하면서 참고 조문을 근거에 넣음 | 지시문 수정은 시험 후 채택 안 함 |
