# 응답시간 최적화 검증 — 2026-11-12

결론: 임베딩 중복 제거는 로컬 처리를 줄였지만 실제 전체 응답시간 단축은 확인되지 않았다. 사용자의 조건(속도 개선과 품질 유지)을 충족했다고 판단할 수 없어 기본 앱 적용을 보류하고 service.py·rerank.py를 작업 전 파일로 복원했다.

## 실험 범위

- 동일 요청의 동일 텍스트 임베딩을 재사용: 기본 리랭킹 경로에서 2~3회 → 1회.
- 단계별 시간 기록 추가. 후보 수·검색 SQL·임계값·모델·프롬프트·근거 길이·검증 기본값은 유지.
- 개인별/질문 간 캐시를 추가하지 않았다. 리랭킹을 끈 기존 rag.search 경로는 그대로라 최대 2회 계산한다.
- 시험셋은 열거나 재평가하지 않았다. 공개된 데모 질문 3개와 무관한 질문 1개만 사용했다.
- 실제 모델 호출은 사용자에게 로컬 회신 본문의 전송 및 비용을 알리고 명시적 승인을 받은 뒤 실행했다.

## 동작 보존 확인

- 토글·첫 답변 실패·리랭킹 실패 등을 조합한 합성 시나리오 64개: 시간 필드를 제외한 전체 반환값 및 검색/모델 입력 일치.
- 후보 조회의 벡터 직접 전달/기존 계산 경로: SQL·매개변수·결과 일치.
- 실제 DB·KURE-v1을 사용하고 실제 API 응답을 재생한 예시 4개 × 3회 × 기존/후보: 검색 결과·점수·근거·API 요청·최종 결과 일치. 추가 API 호출 없음.
- 이는 변경이 입력/처리 결과를 보존하는지에 대한 확인이다. 기존 답변의 정확성, 미래의 환각 0건, 모든 질문에서 품질 무하락을 증명한 것이 아니다.

## 시간 결과

모델 최초 로딩은 제외했다. 로컬 재생은 API 네트워크 대기와 생성 시간을 제외한 수치다. 실제 전체 응답은 질문별 기존 2회·후보 2회(각 8개 표본)를 교차 실행했다.

| 측정 | 기존 중앙값 | 후보 중앙값 | 기존 p95 | 후보 p95 |
|---|---:|---:|---:|---:|
| 실제 응답 재생, 로컬 처리 | 0.429초 | 0.286초 | 0.518초 | 0.342초 |
| 실제 API 포함 전체 응답 | 6.3초 | 6.7초 | 10.32초 | 12.385초 |

| 예시 | 기존 전체 시간(초) | 후보 전체 시간(초) |
|---|---|---|
| 저축은행 대주주 신용공여 | 5.8 / 5.8 | 10.2 / 6.6 |
| 방카슈랑스 판매비중 | 6.8 / 8.5 | 6.6 / 6.8 |
| 적금 제휴 캐시백 | 11.3 / 7.0 | 10.5 / 13.4 |
| 점심 메뉴 | 4.4 / 4.7 | 4.2 / 3.8 |

처음 실시한 고정 응답 대역 기반 로컬 시험은 중앙값 0.441 → 0.297초였다. 실제 API 응답 재생 시험과는 답변/재검색 분기가 다르므로 두 시험을 합산하지 않는다.

## 해석과 채택 결정

- 로컬 반복 계산 제거의 효과는 약 0.14초였다. 전체 지연의 주원인을 해결하지 못했다.
- 후보 버전의 실제 단계별 기록에서 리랭킹은 약 1.15~5.60초, 첫 답변 생성은 약 0.85~5.03초였다. 재검색 시 키워드 추출·두 번째 답변 생성 시간이 추가됐다.
- 실제 호출은 모델 출력/리랭킹/재검색 여부도 실행마다 달라진다. 예시 4개의 표본으로 후보 코드 때문에 느려졌다고 결론 낼 수 없지만, 전체 속도가 유지·개선됐다고 주장할 수도 없다.
- 새로 생성한 실제 답변의 문구와 인용은 실행마다 달랐다. 별도 업무 전문가의 정확도·충실도 채점은 실시하지 않았다. 재생에서 결과가 같다는 것과 독립 생성에서 품질을 입증하는 것은 구분해야 한다.
- 기준을 완화하거나 좋은 실행만 골라 보고하지 않았다. 기본 앱 적용 보류, 기존 파일 복원.

## 다음 단계

더 큰 단축은 리랭킹/답변 API 구간에서 찾아야 한다. 다만 모델 교체, 후보 축소, 근거 축약, 리랭킹 제거는 답변 품질에 영향을 줄 수 있어 이번 작업에서 적용하지 않았다. 먼저 실제 업무 질문의 사람 평가 기준을 마련한 뒤 변경을 하나씩 비교해야 한다. 앞서 발견한 출력 검사·평가 설계 문제도 이번 성능 실험과 섞지 않았다.
