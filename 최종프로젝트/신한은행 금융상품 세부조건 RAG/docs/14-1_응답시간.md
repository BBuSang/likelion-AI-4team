# 14-1 응답 시간 측정

## 왜
- 팀 Agent에 연결하고 서비스로 쓰려면 질문 하나에 얼마나 걸리는지, 어디서 시간이 드는지 알아야 함
- 지금까지는 정확도만 재고 시간은 잰 적이 없음

## 방법 — `analysis/s34_latency.py`
- 지금 서비스 경로 그대로 재요.
  - 상품명 찾기 → 검색(결합 순위 + 섞기) → 점수형 재순위 → 판매 상태 → 답변 생성
  - 답변 원칙은 v9, 근거는 5개예요. 비교 질문은 상품마다 3개씩 가져와요.
- **캐시 없이** 쟀어요. 질문 벡터, 상품명 고르기, 재순위 캐시를 비우고, 캐시 파일 쓰기는 임시 폴더로 돌렸어요.
- 질문은 **한 번에 하나씩** 처리했어요. 한 사람이 물었을 때의 시간이에요.
- 답변은 스트리밍으로 받아 **첫 글자가 나오는 시간**도 쟀어요.
- 질문은 최종 검증 세트에서 유형별로 40개를 골랐어요 (seed 20261201).
  - 상품 사실 14 · 공통 약관 3 · 공용 설명서 3 · 없는 값 6
  - 판매 중지 3 · 판매 중 2 · 판매 중지 줄임말 2 · 가짜 상품 3 · 비교 4
- 환경
  - 맥 로컬: 임베딩 KURE-v1(MPS), 색인은 메모리 (DB 미사용)
  - LLM: `.env`의 CHAT_MODEL, 재순위·상품명 고르기·답변 모두 같은 모델

## 결과 (40개, 초)
| 단계 | 중앙값 | p90 | 최대 | 전체 시간 중 비중 |
|---|---|---|---|---|
| **전체** | **14.2** | **20.3** | 25.5 | |
| 답변 첫 글자까지 | 12.9 | 18.9 | 23.5 | |
| 점수형 재순위 (LLM) | 5.9 | 10.8 | 14.5 | **44%** |
| 답변 생성 (LLM) | 4.6 | 6.2 | 11.4 | 31% |
| 코드 (BM25·결합 순위·상품명 찾기 대조·근거 머리) | 2.4 | 3.3 | 5.3 | 17% |
| 상품명 고르기 (LLM, 필요할 때만) | 0.0 | 3.5 | 6.9 | 5% |
| 질문 임베딩 (로컬) | 0.2 | 0.4 | 1.0 | 2% |

| 유형 | 전체 시간 중앙값 | LLM 호출 |
|---|---|---|
| 상품 사실 · 공통 약관 · 공용 설명서 · 없는 값 | 13.0~13.7 | 2회 (재순위 + 답변) |
| 판매 중지 · 판매 중 | 10.4 · 12.0 | 2회 |
| 판매 중지 줄임말 · 가짜 상품 | 15.4 · 19.3 | 3회 (+ 상품명 고르기) |
| 두 상품 비교 | 21.1 | 3회 (상품마다 재순위, **차례로** 실행) |

- 시작 준비는 서버를 띄울 때 한 번만 해요. 색인 2.7s, 상품명 색인 2.9s, 임베딩 모델 8.3s예요.
- 답변 생성 4.6s 중 약 3.4s는 **첫 글자가 나오기 전 대기**예요. 글자가 나오기 시작하면 약 1.1s 안에 끝나요(출력 중앙값 137자).
- 답변 입력은 중앙값 약 3,200자예요.

## 해석
- **시간의 3/4이 LLM 호출**이에요. 그중 재순위가 가장 커요(후보 10개 × 최대 1,500자를 읽고 점수를 매김).
- **스트리밍만으로는 체감 시간이 거의 줄지 않아요.** 첫 글자가 12.9s에 나오는데, 그 전에 재순위가 끝나야 하기 때문이에요.
- 비교 질문은 상품마다 재순위를 **차례로** 불러서 재순위 시간이 두 배가 돼요(11s).
- 코드 2.4s는 생각보다 커요. 한 질문에 상품명 찾기·BM25·순위 계산을 여러 번 다시 하고 있어요(근거 고르기, 판매 상태, 추정 표시가 각각 상품명 찾기를 부름).

## 줄일 수 있는 곳 (아직 하지 않음 — 정확도와 함께 재야 함)
| 방법 | 예상 효과 | 정확도 위험 |
|---|---|---|
| 비교 질문의 상품별 재순위를 동시에 | 비교 질문 약 −5s | 없음 (같은 호출을 동시에) |
| 한 질문 안에서 상품명 찾기·순위 결과 재사용 | 코드 −1~2s | 없음 (같은 계산) |
| 재순위 후보 글자 수 줄이기 (1,500 → 600자 등) | 재순위 일부 | 있음 — dev로 Hit@k 확인 필요 |
| 재순위·상품명 고르기에 더 빠른 모델 | 재순위 크게 | 있음 — 재순위 안정성(6-3)과 dev Hit@k 다시 확인 |
| 재순위 생략(점수가 확실할 때만) | 경우에 따라 −6s | 있음 — 공통 약관 질문(10-1)이 재순위에 기대고 있음 |

## 정확도에 영향 없는 두 가지 개선 → 다시 측정
1. **형태소 분석기를 한 번만 만들기**
   - 코드 시간 2.4s는 거의 다 BM25용 Kiwi에서 나왔어요. 호출할 때마다 새로 만들어 한 번에 약 0.3s가 들었고, 한 질문에 3~4번 불렀어요.
   - 한 번 만든 것을 다시 쓰고, 같은 글의 BM25 점수는 한 번만 계산하도록 바꿨어요 (`s10_chunks.kiwi_tokens`, `s12_retrieval.bm25`).
2. **비교 질문의 상품별 재순위를 동시에** 부르게 바꿨어요 (`s15_answer_eval.context_ids`).
   - 결과 순서는 그대로예요.
   - 동시에 돌 때를 대비해 Kiwi와 임베딩 계산은 한 번에 하나씩만 실행돼요.

**결과가 같은지 확인** (LLM 캐시 사용)
- 최종 세트 질문 280개의 토큰화: 280/280 같음
- 판매 상태·비교·가짜 상품 질문 80개의 근거 5개: 80/80 같음
- 최종 세트 검색 점수: 보완 Hit@1 0.925 · Hit@5 0.988 그대로

| 같은 40문항 (캐시 없이) | 전 | 후 |
|---|---|---|
| **전체 중앙값 · p90** | 14.2s · 20.3s | **10.3s · 16.1s** |
| 답변 첫 글자까지 중앙값 | 12.9s | 9.1s |
| 코드 중앙값 | 2.4s | **0.0s** |
| 두 상품 비교 중앙값 | 21.1s | **10.7s** |
| 재순위 · 답변 생성 중앙값 | 5.9s · 4.6s | 5.8s · 4.0s (LLM 쪽은 그대로, 차이는 네트워크·모델 변동) |
- 이제 시간은 거의 모두 LLM이에요: 재순위 약 6s + 답변 약 4s.
- 비교 질문은 재순위를 동시에 불러 전체 시간보다 재순위 합이 커요. 그래서 비중 계산에서 코드가 음수로 나와요.
- 더 줄이려면 재순위·답변 LLM 쪽을 손대야 해요. 후보 글자 수, 더 빠른 모델, 재순위 건너뛰기가 있는데 모두 정확도를 다시 재야 해요.
- 측정 기록: 전 `data/eval/latency_before.jsonl`, 후 `data/eval/latency.jsonl`

## 재순위 시간 줄이기 시험 (dev에서만, 기준을 먼저 적음)
- 재순위가 남은 시간의 절반 이상이에요(약 6s). 지금 모델(CHAT_MODEL)은 추론 모델이라 답하기 전에 생각하는 시간이 있어요.
- 같은 모델로 두 가지를 바꿔 봐요. 모델을 바꾸는 건 재순위 안정성(6-3)부터 다시 재야 해서 이번에는 하지 않아요.

| 방식 | 바꾸는 것 |
|---|---|
| 지금 | 후보 10개 × 최대 1,500자, 추론 기본값 |
| 추론 끔 | `reasoning.effort=none` |
| 짧게 | 후보마다 최대 800자 |
| 추론 끔 + 짧게 | 둘 다 |

- **세트**: dev만 써요 — 검색 dev 105 · 공통 약관 dev 45 · 실제 말투 dev 34. 잠금 세트는 쓰지 않아요.
- **시간 재기**: 방식마다 같은 30문항으로 재순위 호출을 하나씩 차례로 불러 중앙값을 재요(캐시 없이).
- **고르는 기준** (결과 보기 전에 기록)
  - 정확도: 세 dev 세트 각각 보완 Hit@1·Hit@5가 지금보다 **1문항 넘게 떨어지지 않아야** 해요.
  - 시간: 재순위 중앙값이 **30% 이상 줄어야** 해요.
  - 둘 다 만족하는 방식 중 가장 빠른 것을 골라요. 없으면 지금 방식을 유지해요.

### 결과 — `analysis/s35_rerank_speed.py` (`data/eval/rerank_speed.json`)
| 방식 | 검색 dev 105: H@1 · H@5 | 공통 약관 dev 45: H@1 · H@5 | 실제 말투 dev 34: H@1 · H@5 | 재순위 시간 중앙값 (p90) | 판정 |
|---|---|---|---|---|---|
| 지금 | 94 · 103 | 36 · 40 | 31 · 34 | 5.21s (6.45s) | |
| 추론 끔 | 94 · 102 | 35 · 41 | **27** · 33 | **2.27s** (2.72s) −56% | 미달 — 실제 말투 H@1 −4 |
| 짧게 800 | 93 · 103 | 36 · 41 | 31 · 34 | 5.64s (8.18s) | 미달 — 빨라지지 않음 |
| 추론 끔 + 짧게 | **92** · 103 | 35 · 40 | **29** · 34 | 2.41s (2.92s) −54% | 미달 — dev H@1 −2, 실제 말투 H@1 −2 |
- 숫자는 보완 기준 맞힌 문항 수예요.
- **기준을 넘은 방식이 없어 지금 방식을 유지해요.**
- 추론을 끄면 재순위가 절반 이하로 빨라져요(5.2s → 2.3s).
  - 대신 실제 말투(반말·오타·붙여 쓰기) 질문에서 1위가 4개 줄었어요.
  - 정돈된 질문(검색 dev)은 그대로였어요. 흐트러진 질문일수록 생각하는 단계가 순위를 지켜 주는 것으로 보여요.
- 글자를 줄여도 시간은 줄지 않았어요. 재순위 시간은 읽는 양보다 **추론 단계**에서 나와요.

### 추가 시험: 추론 'low' (결과 보기 전에 기록)
- 추론을 끄면 빠르지만 실제 말투에서 떨어졌어요. 그 중간인 `reasoning.effort=low`를 같은 방법으로 시험해요.
- **기준은 위와 같아요.**
  - 정확도: 세 dev 세트 각각 보완 H@1·H@5가 지금보다 1문항 넘게 떨어지지 않아야 해요.
  - 시간: 재순위 중앙값이 30% 이상 줄어야 해요.
- 시간은 시간대 차이를 없애려고 '지금' 방식과 같은 30문항으로 번갈아 다시 재요.
- 이 시험은 앞 시험의 결과를 본 뒤 추가한 것이에요. 그래서 통과해도 dev 결과를 보고 고른 방식이라는 점을 함께 적어요.

**결과** (`data/eval/rerank_speed_low.json`)
| 방식 | 검색 dev 105: H@1 · H@5 | 공통 약관 dev 45 | 실제 말투 dev 34 | 재순위 시간 중앙값 (p90) | 판정 |
|---|---|---|---|---|---|
| 지금 (같은 시점에 다시) | 93 · 103 | 36 · 40 | 31 · 34 | 4.87s (7.78s) | |
| 추론 low | 94 · 103 | **34** · 41 | 30 · 34 | 3.58s (4.81s) **−26%** | **미달** — 공통 약관 H@1 −2, 시간 30% 미만 |
- **지금 방식을 유지해요.** 'low'는 시간 기준(30% 이상)도 넘지 못했어요.
- '지금' 방식의 검색 dev H@1이 앞 시험(94)과 이번(93) 사이에 1개 달라졌어요.
  - 같은 설정이어도 캐시에 없는 호출이 생기면 LLM 결과가 조금씩 흔들려요(6-3 재순위 안정성 94%).
  - 그래서 1문항 차이는 측정 오차 범위로 봐야 해요.
- 정리: 추론을 줄일수록 재순위는 빨라져요(5s → 3.6s → 2.3s). 대신 공통 약관과 실제 말투 질문의 1위가 먼저 흔들려요.
  - 이 둘은 10-1과 12-1에서 공들여 지킨 부분이라, 재순위 추론은 그대로 두는 것으로 결정했어요.
