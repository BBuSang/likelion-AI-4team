# 5-1 검색 평가셋과 검색 방식 비교 (2026-11-11)

## 평가셋 (`analysis/s11_evalset.py` → `data/eval/retrieval_dev.jsonl`·`retrieval_test.jsonl`)
- **A형 상품 지정 사실 질문 147개**: 정형 문구가 아닌 섹션을 문서 종류별로 층화 표본(설명서 80·특약 30·투자설명서 12·간이 8·약관 12·약정서 8, 한 문서에 몰리지 않게 문서를 돌아가며) → CHAT_MODEL이 **영업점 직원 말투**로 질문(상품명 포함, 원문 베끼지 않기)·짧은 답·근거 원문 작성. 정답 = 그 문서의 그 섹션
- **B형 공통 조항 20개(절반은 상품명 포함)·용어 10개**: 정답 = 그 공통 조항·용어
- 근거 원문이 정답 섹션에 그대로 없으면 버림 (3개 버림) → **177개**
- **dev 105 / test 72 — 상품 단위로 나눔**(같은 상품이 양쪽에 없음). test는 방식을 고를 때 보지 않고 마지막에 한 번만 채점
- dev 표본 24개 직접 읽어 검수: 실제 직원 질문처럼 자연스럽고 답이 원문에 있음. 다만 약정서 시행일·우선 설명 대상 연령처럼 덜 중요한 질문도 섞임
- 비교·SQL 질문, 판매 중지·미보유 값 질문은 **답변 단계 평가에서** 따로 만듦 (검색 지표에 넣지 않음)

## 검색 방식 (`analysis/s12_retrieval.py`)
| 방식 | 설명 |
|---|---|
| vec | 임베딩 코사인 |
| kw | BM25 (Kiwi 형태소) |
| hybrid | vec + kw 순위 결합 (RRF k=60) |
| routed | 질문에서 상품명을 찾아 그 상품의 문서 청크 + 그 문서의 공통 조항 + 용어집으로 좁힌 뒤 hybrid |
| rerank | routed 상위 10개를 CHAT_MODEL이 "질문에 직접 답하는 순서"로 다시 줄 세움 |
- 정답 판정: 정답 섹션 번호가 든 청크(같은 문서) / 정답 공통 조항·용어. 지표 Hit@1·Hit@5·MRR@10

## dev 결과 (방식 고르기, 105개)
| 방식 | 전체 H@1 | 전체 H@5 | MRR | A형 H@1 | A형 H@5 |
|---|---|---|---|---|---|
| vec | 0.295 | 0.629 | 0.436 | 0.276 | 0.609 |
| kw | 0.429 | 0.762 | 0.564 | 0.460 | 0.770 |
| hybrid | 0.390 | 0.800 | 0.552 | 0.379 | 0.805 |
| routed (처음 별칭) | 0.457 | 0.857 | 0.621 | 0.437 | 0.851 |
| routed (별칭 보완) | 0.438 | 0.886 | 0.614 | 0.414 | 0.885 |
| **rerank** | **0.705** | **0.952** | **0.815** | 0.736 | 0.966 |
- 벡터만으로는 상품을 못 가림(4-2에서 본 '운동화 적금' 문제) → 키워드가 벡터보다 좋고, **상품명으로 좁히기**가 H@5를 크게 올림
- 상품명 찾기 보완(dev 실패 15건을 보고 **일반 규칙**으로): 연결 문서 제목·괄호 안 이름(헤이영·썸데이)·이름 뒤쪽 어절(스타트업 통장·골드테크)을 별칭으로, 4개 이상 상품에 겹치는 별칭(정기예금·통장)은 버림, '신한은행'을 '신한'보다 먼저 뺌 → dev 상품명 찾기 79/94 → 91/94
- **재순위가 1위 적중을 0.44 → 0.71로** 가장 크게 올림 → **rerank로 확정** (test 채점 전)

## test 결과 (한 번만, 72개)

- 재순위 효과는 test에서도 유지 (H@1 0.361 → 0.583)
