| 정형 추출 | LLM으로 130개 문서에서 금리 839 · 수수료 176 · 혜택 226개, 항목마다 근거 섹션·원문 문장 |

| 검색 | 상품명으로 좁히기 + 벡터·키워드 결합(RRF) + 재순위 후보 섞기(지금 순위 7 + 상품 이름을 뺀 주제 순위 3) + 점수형 재순위, 상위 5개 근거. 질문이 여러 개면 질문마다, 비교는 상품마다 근거 |
| 답변 | 답변 원칙 v9 (근거마다 문서 층·상품 연결 표시, 모순일 때만 상품 특약 우선, 없는 값은 지어내지 않고 확인할 곳 안내, 판매 상태 목록 대조, 비교 질문은 상품마다 근거, 판매 중지 이름도 상품명 후보, 이름 앞뒤 낯선 말이면 LLM 확인, 추정 표시는 코드로 보장) |
| 답변 표시 (코드) | 대상 상품·판매 상태 한 줄, 실제 인용한 근거 문서, 함께 볼 문서(재순위 1점 이상) |
| 응답 시간 | 중앙값 10.3초 · p90 16.1초 (대부분 재순위·답변 LLM) |
| 남은 약점 | 실제 상품 정식 이름에 말을 덧붙인 가짜 상품에 실제 상품을 붙임(최종 검증 1/20), 평가 질문이 모두 LLM이 만든 질문 |

**최종 방식: KURE-v1 + 상품명 좁히기(별칭, 못 찾으면 후보 → LLM 고르기) + 벡터·키워드 결합 + 재순위 후보 섞기 + 점수형 재순위 + 판매 상태 목록 대조 + 질문 나누기 + 답변 원칙 v9.**
은행 직원이 고객에게 그대로 안내하는 답이라 **지어내지 않는 것**을 1순위로 봤어요. 그래서 검색 1위 적중보다 같은 질문에 같은 근거가 나오는 안정성, 문서에 없을 때 정확히 거절하는지를 따로 쟀어요.

| Python | 3.13, 맥 (MPS) |

### 데이터 관찰 메모
- 금감원 API의 우대조건은 중앙값 72~108자로 짧아요. "대중교통 미션 연 0.4%p"만 있고 **무엇을 해야 인정되는지(카드 종류·급여이체 기준·중도해지 시 우대 미적용)는 설명서에만** 있어요 → API를 빼고 설명서 기반으로
- 대출 270개 대부분은 상품 전용 설명서가 없고 **공통 설명서를 공유**해요 (가계대출 설명서 하나에 85개 상품). 공통 설명서의 상품별 수치는 빈칸 서식이에요
- 기한의 이익 상실 시점처럼 **대출 유형마다 다른 규칙**이 있어요 → 상품 → 연결 설명서로 좁힌 뒤 답해야 함
- 요약 상품설명서 쪽이 본문과 다른 경우가 있어요 (예금자보호 5천만원 vs 본문 1억원) → 본문 우선, 요약 쪽 제외
- 문서 형식 5종: 표형 109 · 조문형 117 · 목차형 · 투자설명서형 · 기타
- 같은 문구가 수십 개 문서에 반복돼요 (자료열람요구권 58개, 위법계약해지권 48개) → 그대로 청크로 넣으면 검색 상위를 덮어요
- 판매중지 날짜는 대출 목록에만 있어요 (1,338건 중 91건) → 날짜는 답하지 않고 판매 중지 사실만
- 이미지뿐인 설명서 1개는 OCR이 필요하고, 이미지에 **다운로드 워터마크(가려진 이름·ID)**가 찍혀 있어요

### 진행 원칙
- **방식은 dev로만 고르고, 잠근 세트는 다 정한 뒤 한 번만 채점** — 섹션 분할·검색·답변·없는 값·상품명 찾기 모두 같은 원칙
- 잠근 세트를 보고 고치면 그 세트는 오염된 것으로 보고 **새 세트를 만들어** 다시 잼
- 개선 전에 **통과 기준을 먼저 기록**하고, 기준에 못 미치면 그대로 적음
- LLM 출력은 코드로 검사할 수 있게 근거(섹션 번호·원문 문장)를 함께 받음
- 측정하지 않은 수치는 쓰지 않음, LLM 채점은 원문과 대조해 다시 확인 (누가 대조했는지 함께 적음)

## 3. 작업 과정 (시간순)

### 3-1. 주제·범위 결정
- 팀 Agent 안에서 다른 팀원 RAG(법규·사례)와 겹치지 않는 **금융상품 세부조건**을 맡았어요
- 금감원 API와 시험 3개 은행 설명서를 비교해, 금리는 같지만 **우대조건 인정 기준은 설명서에만** 있다는 걸 확인 → API 제외
- 직원은 자기 은행 상품을 안내하니 **신한은행 하나, 상품공시 전체**로 정했어요
- 받아온 추출 스키마는 상품↔문서 1:N이라 공유 설명서를 표현하지 못해서 **N:M·문서 기준**으로 고쳤어요

### 3-2. 데이터 수집과 검증
- 고시 금리: 상품을 바꾼 직후 화면을 읽으면 **이전 상품 행이 섞이는 문제**(신용대출 130행 중 45행)를 찾아 "표가 3번 연속 같을 때까지 기다리기"로 다시 수집 → 대출 산식 170/172 일치, 적금 26개 중 25개가 설명서와 일치
- 판매 중지 목록 1,338건 전체 수집 (탭별 사이트 총건수와 일치)
- 이미지뿐인 설명서 1개를 macOS Vision으로 로컬 OCR (1,332자 → 17,675자), 텍스트에 섞인 워터마크를 지우고 다시 실행
- 파이프라인을 2번 돌려 결과 파일 751개의 해시가 같은지 확인 (재현성)

### 3-3. 전처리 (코드만)
- 반복 문구(심의필·유효기간·안내문) 3,082줄 제거, 247개 모두 숫자 보존 확인
- **섹션 분할**: 형식별 제목 규칙 + 표형 행 이름 사전. 사람이 섹션 시작 줄을 표시한 정답으로 쟀고, **규칙을 고치기 전에 무작위로 고른 잠금 시험 7개**를 마지막에 한 번 채점
- **줄바꿈 복원**: PDF 폭 때문에 끊긴 줄을 이을 때 띄어쓸지를 어절 빈도 + Kiwi 형태소로 판단. 긴 줄을 무작위로 잘라 복원하는 시뮬레이션으로 쟀어요 (문서 절반으로 고르고 나머지 절반에서 확인). 글자는 바꾸지 않고 공백·줄바꿈만 조정
- **공통 조항 분리**: 3개 이상 문서에 같은 문구(숫자 완전히 같음, 다른 글자 4자 이하)를 묶음. 섹션은 지우지 않고 표시만

### 3-4. LLM 정형 추출
- LLM 일을 "숫자·조건을 칸으로 옮기기"로 좁혔어요 (섹션·기준일은 코드가 이미 처리)
- 항목마다 **근거 섹션 번호와 원문 문장**을 받고, 코드로 문장이 그 섹션에 있는지·숫자가 그 문장에 있는지 검사
- 형식이 다른 6개 문서로 3번 시험 (1차 문제 7가지 → 지시문 반영 → 2차에서 산식 금리 누락 → 3차 해결) 후 130개 전체
- 원문 대조 중 **정형 문구 분리 규칙이 상품 사실(예금자보호 여부)까지 삼킨 문제**를 찾아 규칙을 고치고 26개 문서를 다시 추출

### 3-5. 청크·임베딩
- 정형 문구가 아닌 섹션을 같은 큰 제목 안에서 300자 이상으로 묶고, 1,500자를 넘으면 나눔. 머리말 `[문서 제목] 섹션 경로 (p.쪽)`
- 처음엔 OpenAI 임베딩을 썼는데, 같은 dev에서 KURE-v1이 재순위 전 모든 단계에서 앞서 **KURE로 교체**. 코랩 GPU로 만들고, 이후 맥에서도 직접 실행 (코랩 벡터와 코사인 1.0)

### 3-6. 검색 평가 세트와 방식 고르기
- 섹션마다 직원 말투 질문을 LLM으로 만들어 177개 (dev 105 / test 72, 상품 단위로 나눔)
- 벡터 / 키워드(Kiwi BM25) / 결합(RRF) / 상품명으로 좁히기 / LLM 재순위를 dev로 비교
- **Hit@1이 낮아 보인 이유**를 따라가 보니 정답이 '질문을 만든 섹션 하나'뿐이라, 같은 답을 담은 특약·공통 약관이 1위여도 오답으로 셌어요 → 후보를 모아 LLM이 '같은 답'을 표시(사람 검수 13/14)한 **보완 지표**를 추가. 보완 Hit@1이 답변 기준 정확도(91%)와 맞아떨어짐
- **재순위 흔들림**: 후보 순서만 섞어도 1위가 바뀌었어요(1위 일치 71%). 후보 순서를 고르게 하는 대신 **후보마다 0~3점**을 매기게 바꿔 1위 일치 94%. 1위 적중은 조금 낮았지만 답변 정확도는 같아서 점수형으로 확정

### 3-7. 답변 원칙과 답변 평가
- 상위 k개 근거로 답을 만들고 LLM이 채점, 일부는 사람이 다시 읽음
- 답이 맞는데도 "이 상품에 적용되는지 확인되지 않음"이라고 **과하게 유보**하는 문제 → 근거마다 문서 층(설명서·특약·공통 약관)과 질문 상품에 연결된 문서인지를 붙여 줌
- 문서끼리 값이 다를 때 → **모순일 때만 상품 특약 우선** (각 특약 제1조 + 예금거래기본약관 제23조 '약관적용의 순서'). 다른 상황을 다루는 조항은 앞세우지 않음

### 3-8. 잠금 test 채점 → 새 test2
- test에서 실패 1건이 상품명 별칭 오류였어요. 이걸 고치면 test가 오염되므로, 고친 뒤 **dev·test에 쓰지 않은 상품으로 test2 98개**를 새로 만들어 다시 잼 (절반은 줄임말로 상품을 부르게)

### 3-9. '없는 값' 평가
- 지금까지는 답이 문서에 있는 질문만 쟀어요. **답이 없을 때 지어내는지**를 재려고 4가지 유형 60개를 만들었어요: 전용 문서에 없는 값 / 공통 문서만 있는 대출의 상품별 값 / **예시 숫자 함정**(공통 설명서의 해약금률 1.4% 계산 예시) / **가짜 상품**
- 정답이 '없음'이라 "정말 없는지"가 가장 중요 → LLM 확인 + 60개를 사람이 전부 읽어 가짜 상품 이름 누락, 빈칸만 묻는 질문, 함정 힌트("실제로")를 고치고 7개를 뺌
- dev에서 지어냄은 0이었지만 안내 문구를 개선 (v5): 이미 본 설명서를 다시 보라고 하지 않고 여신 시스템·영업점 안내, 상품명을 못 찾으면 "목록에서 찾지 못함 → 정식 이름 확인". 답이 있는 dev 105개에서 판정이 바뀐 답 7개를 사람이 읽어 새 규칙 때문에 나빠진 답이 없음을 확인

### 3-10. 줄임말 상품명 찾기
- 별칭 정확 일치만으로는 직원 줄임말('마이카대출', '밸류업 외화예금')의 절반을 못 찾았어요
- **과적합 방지**: 줄임말마다 규칙을 넣지 않고 "정확 일치 → 못 찾으면 상품 이름 임베딩 + 글자쌍 후보 20개 → LLM 고르기" 하나로. **구현 전에** 잠금 세트(줄임말 60 · 가짜 30 · 공통 질문 20)와 통과 기준을 먼저 기록
- dev에서 가짜 상품 1개에 실제 상품을 붙여서 일반 원칙 한 줄("상품 종류 말만 겹치면 고르지 않음")만 추가
- 추정으로 찾은 상품은 답변 첫머리에 "질문하신 '○○'을 '△△'으로 보고 답합니다"라고 밝히게 함 (잘못 짚으면 직원이 바로 알아채도록)

### 3-11. 1단계 별칭 오탐 개선
- 남은 오탐(틀림·가짜 상품)이 모두 1단계 별칭에서 나와 원인을 분석: ① 상품 정식 이름이 아니라 일부에서 만든 별칭이거나 ② 그 별칭을 이름에 품은 다른 상품이 있을 때 틀림 → 두 신호가 있으면 바로 확정하지 않고 LLM이 확인 (dev 오탐 6개 전부 해당, 바로 확정되는 경우는 모두 맞음)
- 9-1 잠금 세트를 보고 찾은 문제라 **구현 전에 새 잠금 세트**(이름이 비슷한 상품의 줄임말 40 · 그 밖 20 · 정식 이름 20 · 실제 별칭 단어를 품은 가짜 30 · 공통 20)를 OpenAI로 만들고 통과 기준을 먼저 기록

### 3-12. 가짜 상품 오탐 개선
- 남은 유형은 실제 상품의 고유한 이름에 지어낸 말을 붙인 가짜('청춘 청년처음적금플랜') → LLM 확인 지시에 "호칭 안의 고유한 말은 모두 후보 이름과 대응해야 함" 원칙 추가, LLM 확인을 거친 상품은 답변에 '(추정)'을 밝힘
- dev에서 두 판을 비교: 원칙만 넣은 첫 판(가짜 17 → 7) vs LLM이 '대응 없는 말'을 적게 해 코드로 거른 둘째 판(7 → 6, 대신 진짜 줄임말 3개를 더 놓침) → **첫 판 선택**
- 다시 **구현 전에 새 잠금 세트 4**(가짜 60 · 줄임말 40 · 정식 이름 20 · 공통 10)를 만들고 기준을 기록

### 3-13. 공통 약관에만 있는 답 놓침 개선
- test2 실패 2건의 원인: 상품 문서 조각은 머리에 상품 이름이 붙어 있어, 질문에 상품 이름이 있으면 주제와 상관없이 그 상품 조각이 위로 올라오고 공통 약관 조각은 재순위 후보(상위 10)에 못 들어옴
- dev에 이런 질문이 8개뿐이라 **새 세트**(상품 이름으로 묻지만 답은 공통 약관에만 있는 질문 + 상품 전용 질문, dev/test)를 OpenAI로 만들고 기준을 먼저 기록
- dev 비교: '상품 이름을 뺀 주제만으로 순위'는 공통 약관을 가장 잘 찾았지만 상품 전용 질문의 1위를 크게 떨어뜨림(dev 105 보완 H@1 0.905 → 0.819) — 상품 이름은 범위 안에서도 "그 상품 문서 먼저"라는 신호였음 → **재순위 후보를 지금 방식 7 + 주제 순위 3으로 섞는 방식** 선택

### 3-14. 판매 중지·상품 비교 평가 → 판매 상태 확인
- 처음 재는 유형이라 평가 세트(판매 중지 30 · 양쪽 이름 10 · 판매 중 10 · 두 상품 비교 23, dev/test)를 OpenAI로 만들고 지금 방식으로 dev 기준선을 잼 → 판매 중지라고 말한 답 **0/15**, 비교 질문 4/15 (두 상품 중 하나만 찾음)
- 원인: 판매 중지 목록(1,338건)이 있는데 검색·답변에서 쓰지 않음. 판매 중지된 '신한 희망대출'을 판매 중인 '새희망드림대출'로 추정하는 위험 사례도 발견
- 판매 여부는 문서에서 찾을 정보가 아니라 **목록에서 조회할 사실**이라 보고, 질문 속 이름을 판매 중·판매 중지 목록과 대조해 `[판매 상태]`를 답변에 주고(답변 원칙 v6), 판매 중지 이름이면 다른 상품으로 추정하지 않게 함
- 비교 질문은 상품명 찾기가 가장 긴 별칭 하나만 잡아 **두 상품 중 하나만** 찾던 것이 원인 → 질문 속 겹치지 않는 별칭을 모두 찾고, 근거를 상품마다 나눠 가져오고(상품당 3개), 상품마다 그 상품 근거에서만 값을 가져오게 함(답변 원칙 v7)
- 빈틈 확인(새 세트): 판매 중지 상품을 **줄임말**로 부르면 판매 중지라고 안내 0/15, 비슷한 판매 중 상품 정보로 답함 3/15 → 상품명 찾기 후보에 **판매 중지 이름 440개도 넣어**(판매 중 후보는 그대로 두고 따로 더함) LLM이 판매 중지 상품을 고르면 판매 중지로 안내, 판매 중·중지가 애매하면 둘 다 알리게 함(v8)
- 정식 이름 **전체**를 품은 가짜 상품('꽃온 Npay biz 신한통장')은 1단계가 바로 확정해 표시 없이 실제 상품 정보로 답함 → 맞은 이름 바로 앞뒤에 붙은 명사가 있으면 LLM 확인으로(Kiwi 품사, 신호 ③), 추정으로 찾은 답변에는 **코드가 추정 표시를 붙임**(모델이 빼먹어도) (v9)

### 3-15. 실제 말투 평가
- 지금까지 평가 질문이 대부분 단정한 문장이라, **같은 사실을 단정한 말투와 실제 말투(짧은 반말·줄임말·오타·붙여 쓰기·고객 상황·질문 두 개·구어체 숫자)로 함께 묻는 짝 비교 세트**를 만들어 말투의 영향만 따로 잼 (상품 사실·공통 약관·없는 값·판매 중지·비교)

### 3-16. 최종 검증
- 시험 세트가 작아 1문항 차이로 기준을 넘거나 못 넘는 일이 반복돼, **모든 질문 유형을 한 세트(280문항)에 모아** 코드를 고정한 채 한 번만 채점 (세트 구성과 기준을 먼저 기록)
- 정답 섹션은 모두 새것. 단 공통 약관 7개는 새 섹션이 3개뿐이라 예전 정답 조항을 다른 상품·새 질문으로 묻고, 공용 대출 설명서 질문을 따로 둠
- 10-1 교훈대로 공통 약관·공용 설명서 후보 59개를 원문과 대조해 **조항이 그 상품에 적용되지 않는 것 등 11개를 결과 보기 전에** 뺌

### 3-17. 응답 시간 측정
- 서비스로 쓰려면 시간이 어디서 드는지 알아야 해서, 지금 경로 그대로 **캐시를 비우고** 질문을 하나씩 처리하며 단계별 시간을 잼 → 시간의 3/4이 LLM 호출, 그중 재순위가 가장 큼

### 3-18. 질문 두 개
- 최종 검증 실패 중 '질문 두 개'가 많아 새 세트(같은 상품의 새 섹션 2개를 한 메시지로, dev 24 · test 30)를 고치기 전에 만들고 기준을 먼저 기록
- 기준선을 읽어 보니 답변은 두 질문에 각각 답하고 있었고, 실패 원인은 질문 전체로 근거를 한 번만 찾아 한쪽 주제 근거가 밀린 것 → 답변 규칙 대신 **질문을 코드로 나눠(물음표·'그리고') 질문마다 근거를 찾도록**(두 번째 질문은 전체 질문에서 찾은 상품으로 범위를 좁힘, 재순위는 동시에)
